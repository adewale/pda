# A second Poppy client, and stateful tests of our mock Company

Our TypeScript client (`src/poppy/`) and our mock Company (`test/mock-company/`) were written by the same people under the same readings of the text, so a misreading they share passes every test. This directory checks the mock from outside, with:

- **an independent Poppy client in Python** (`poppy_client.py`) that speaks Poppy 0.4, written from the 11 November text (`spec/draft-0.4-retrieved-2026-11-11/`) and the `v04-*` rows of our readings (`docs/readings.md`), not ported from `src/poppy`. It covers discovery from the domain's protected resource metadata, including a Company with no issuer (a 404 or no authorization servers: signed out only, identified by `https://{domain}`), `Poppy-Version` and `Poppy-Extensions` on every Session-header request (3.4), Web Bot Auth operator signatures with its own Ed25519 key and signer (5.3), client assertions, the Session header (a delegated key, its delegation and a Session JWT per request), DPoP proofs with nonces and `ath` when the issuer lists ES256, the three sign-in types (Direct, Device, and Mediated Sign-In's grant), refresh tokens with rotation, revocation, conversations with request ids, handoff, cancel and Direct Conversations from invitations (8), Operations 3 with user and agent approvals and declines, MCP with a token for the server's `url`, the browser join with `poppy:browser-sign-in` and website pages fetched with the Session header (5.2, 6), excluded tasks, skills and feedback (9), Device Sign-In polling, and rate limits;
- **six Hypothesis stateful, model-based tests** (`RuleBasedStateMachine`s) that drive it against the mock and hold every response to a model. `machine.py` has the model, the rules they share and the invariants they all hold; each `test_*.py` is one machine. `test_oracles.py` checks, without a Company, that the model's oracles reject wrong answers. `test_findings.py` keeps, as regression tests, the places where the mock departed from the 0.4 text (below).

It was written for Draft 0.1 in October, ported to 0.3 on 29 October ([decision 37](../../docs/decisions.md)) and moved to that version's 3 November text. It was ported to 0.4 on 12 November 2026, from the 11 November text, when the mock it runs against was set to serve 0.4 alone (`protocolVersion: "0.4"` in the launcher's base settings).

**Maintenance.** By the owner's decision on 12 October 2026, this client is maintained only as an occasional local check, run after a change to the text or a large change to the mock Company. It is not expanded feature by feature.

## Running it

```sh
npm run test:hypothesis                                 # default: 100 runs of up to 30 steps per machine
npm run test:hypothesis -- --hypothesis-profile=deep    # 2,000 runs of up to 60 steps per machine
```

It needs `uv` and Node; `uv run --frozen` installs the pinned, hash-locked dependencies from `uv.lock` into `.venv/`. It is local only: not part of `npm test`, not in CI. Everything stays on 127.0.0.1, with no Docker. After dependencies are installed, no external service or paid model is used. These are observations, not runtime promises: the default profile took 99 seconds on 29 October; a deep run of the 0.1 client took 95 minutes with four workers.

Each request is a new loopback connection, so a run leaves many sockets in `TIME_WAIT`. On macOS, a deep run, or default runs back to back, can exhaust the ephemeral ports: requests then fail with `[Errno 49] Can't assign requested address`, which Hypothesis may report as a flaky strategy. Wait until `netstat -an -p tcp | grep -c TIME_WAIT` is low again and rerun.

## How it reaches the mock

`launcher.ts` runs the mock in Node, bundled by `interop/impls/shared/build.mjs` like the interop adapter, under `<id>.company.interop.test`. The Python client's transport sends each `https://` request to 127.0.0.1 with the Company's host in `Host` and `X-Forwarded-Proto: https`, as the interop proxy does, so the mock checks `htu`, `aud` and the issuer against the real URLs. No check is relaxed. The Python agent's client metadata and JWKS, and a second agent's for the reject rules, reach the mock through its `serveClientDocument` and are checked like any other client's.

**The clock.** The client times requests on its own clock (`Clock`), which starts at the real time and moves only when the agent waits. The transport stamps it on every request in `x-test-clock`, the header the mock reads for rate limits, device polling and token age (`CLOCK_HEADER` in `test/mock-company/core.ts`). So waiting out a `Retry-After`, a device `interval` or `expires_in` costs nothing and every timing is exact. JWTs carry the real time, which is what the mock checks them against.

**The client's limiter.** The transport is also the client's one rate limiter for the Company (5.6; the Guides' "Rate limits": share a Company's limits across tasks and Users): after a 429 it sends nothing to the Company until the `Retry-After` has passed. The client resends a refused request with a new Session JWT, proof and client assertion.

The Python agent's operator key directory (`/.well-known/http-message-signatures-directory` on its origin) reaches the mock the same way, so every honest resource request carries an operator signature made by this client's signer and checked by the mock's own verifier. Neither shares code with `src/poppy/operator.ts`, so a misreading of RFC 9421's signature base on either side is a recorded violation.

The launcher's control port has the interop hooks and `GET /violations` of `interop/impls/shared/mock-hooks.ts`, the module the `lenient-company` adapter uses too, `GET /state`, and `POST /reset` with the settings a run draws (`KNOBS` in `launcher.ts`) over a base that serves 0.4 alone: strict or lenient assertions, DPoP-bound or Bearer tokens, rotation and reuse detection, nonces per Company or per origin, token responses without `scope`, an issuer with a trailing slash, no issuer at all, sign-out that ends Sessions, streaming, text deltas, keep-alives, whether the Company Agent replies, refusing writes from agents without the extension, operation ids with the Company's own prefixes (`booking:`, `ord#`, `a/b `, `%41`, accented), a Company that answers an approval with a new revision or declines agent or all approvals (Ops 6), a browser join or none, `web.disabled`, `web.unscoped` (6), feedback answered 202 or with an alternative (9.3), the device `interval` and `expires_in`, and the events per page.

## The machines

Every machine holds four invariants after every step:

- `GET /violations` holds exactly the ids its reject rules expect, in order, and nothing after honest rules.
- The Company's Sessions are the ones our requests started, by `sid` (5.3): each the User's, signed in to the account its last request's token was for, or signed out, and ended as the model says. The model follows the Company's side of each Session as well as the agent's: a Session the Company has seen, the sign-in its last token came from, and the account it was ever used with.
- Over every request the client sent, the Session header went to every resource (APIs, conversations, MCP, the browser join's `authorize`, tasks and feedback) and to website pages of `organization.domain` only where no browser join is listed (5.2), and never to an OAuth endpoint, a skill or a well-known document, but for the reject rules that break it on purpose.
- Every request with the Session header declared `Poppy-Version: 0.4` and its Session's one `Poppy-Extensions` value (3.4: the same for the whole Session), but for the reject rules that change them.

Each run draws whether its Sessions declare `"operations";v="3"`, and the run ends by printing how often each rule reached each outcome, so a rule that stopped firing shows.

Every read of a conversation to its end is held to the log checks in `machine.py`: our messages once each, in order, as sent, each with its request's `id` as its id (8.3); every event read once, in order, resuming from the cursor, JSON and stream alike; every message with `author.type` (8.4); `as_of_request` only on the Company Agent's messages, naming a request this conversation accepted, and `as_of_cursor` only on our agent's own (8.4); a `state` event marks a change in `handoff`, `responder` or `closed`, `pending` only while the responder is `agent` (8.7); a person's message comes after a `state` event saying `human`; nothing after `closed` (8.12); each Direct Conversation opened has `direct_opened` and, once closed however it closed, `direct_closed` (8.10); each `user_requested`, with its reason; no operation for a Session that doesn't declare Operations 3; and each read's four state fields (`working`, `handoff`, `responder`, `closed`) are the model's, a stream's opening with a `working` event that has no id (8.6, 8.7).

### `test_mock_company.py`: Sessions, sign-in, versions, conversations, tasks

Honest rules: discover again; add Users; start Sessions (a new `sid`, nothing requested); switch DPoP keys; sign in by Direct, Device or Mediated Sign-In with any subset of the offered scopes, approved in full or in part, the token going to a Session never used with another account or to a new one (5.4); sign a Session in from a stored refresh token; refresh, perhaps narrower; sign out by revoking the refresh token; meet a Session the Company ended (`session_ended`) and start a new one; send a request without an operator signature (served, nothing recorded); call the OpenAPI reads (a 401 challenge naming the scopes signed out, `insufficient_scope` short of them); start conversations with a request id (`wait` absent, 0 or 1), send with `wait` and `cursor`, retry the same request (members in any order, any spelling; the original `{conversation_id}`), read as JSON or a stream, from the start or the saved cursor, signed in or after sign-out; close (202, also when already closed). Tasks (9): `GET {tasks.endpoint}` with the Session header and no token; `excluded_tasks`; each skill fetched without the Session header and checked against its `sha256` digest, its URL resolved against `tasks.endpoint`; feedback on a task, answered 202 or 200 with an alternative.

Reject rules: a replayed client assertion, DPoP proof (at the token endpoint and at a resource) or Session JWT; any client assertion `aud` but the issuer as a string (4.1); the Session header at an OAuth endpoint; a tampered Session JWT (`typ`, signature, `kid`, `aud`, `htm`, `htu`, `ath`, no `sub` or `sid`) or delegation (longer than a day, naming the User); one delegated key for two User IDs; a DPoP-bound token with another key's proof, or as Bearer; an access token in another agent's Session; a rotated refresh token used again (with reuse detection, its sign-in revoked); a revoked one; one from another client; a second account in one Session (`session_ended`); a sign-in asking for no scope or an unlisted one; an operator signature that doesn't verify, or that leaves out `poppy-session`; no `Poppy-Version` or an unlisted one (400 `version_unsupported`); a Session's `Poppy-Extensions` changed (recorded, served); a request id reused with another path or body (409 `request_id_conflict`); no request id or a malformed one (400 `invalid_request`); `as_of_cursor` on the User's words or naming another conversation's event; a message to a closed conversation; an invalid cursor; a skill fetched with the Session header; tasks with an access token; feedback on an excluded task or repeated, or malformed.

Who may use a conversation is 8.2 and 8.11: its `client_id` and User ID, and, once it used an account, that account too. The same User signed out of it gets a challenge for the account (401, no error code); the same User signed in to another account gets `conversation_not_found`; another User gets `conversation_not_found` too, recorded as a cross-User reach.

### `test_issuerless.py`: a Company with no OAuth issuer

The mock runs with `issuerless` (3.2): no `auth` in `poppy.json`, a 404 for the domain's and the MCP server's protected resource metadata, and nothing on the auth host. Honest rules: discover again (signed out only, identified by `https://{domain}`, no OAuth metadata); the well-known documents are all 404; the OpenAPI reads (200, or a challenge naming the scopes); MCP signed out with no server metadata; conversations, sends, retries and reads; operator signatures as above. Reject rules: a Session JWT addressed to anything but the identifier (the issuer the Company would have, the domain with a trailing slash or in capitals, an API's origin, or a list) is 400 `invalid_session` and recorded as `session-jwt.aud`.

### `test_operations.py`: Operations 3

A write that needs approval is refused with the operation through every channel the mock has: the OpenAPI exchange (403 `approval_required`), the MCP tool (an error result with the operation in `structuredContent`), the Company Agent's message in a conversation that used the account, and the print shop's order (signed out or in, with photos uploaded in that Session). Each operation has its `terms`, and `summary` only if the Company gives one. The same request sent again with an approval naming a revision the Company returned (`Poppy-Approval`, `_meta`, or a message's `extensions.operations.approval`) is performed; sent again, approved, it gets the first response (Ops 7). An approval carries `operation_id`, `revision`, `approver` (`user`, or `agent` where the agent may approve), `approved_at` as an Integer when sent, `input_type` only from the User, and a new `reference`. A Company with `reviseOnFirstApproval` answers the first approval with a new revision; one with `declineApprovals` declines agent or all approvals: 403 `approval_declined` at APIs, an `isError` result whose `structuredContent` has `error` at MCP, and `extensions.operations.declined` without `error` in a conversation, each naming the operation, the revision and a reason. After a decline, or after an agent approval the Company answered with a new revision, only the User approves that operation. An agent without the extension gets the exchange done at once, or `extension_required` in a JSON body naming it.

Reject rules: an approval from a Session that may not approve it (no approval: the Session gets its own operation); an approval naming a revision never returned, or sent with a changed request; the approved request reusing the first request's `Idempotency-Key`; a malformed `Poppy-Approval`, approval members (approver, `approved_at`, `input_type`, `reference`), `_meta` approval or message approval (recorded, and no approval); a `reference` reused for another approval; a declined approval sent again; an agent approval after a decline; an agent approving the revision that answered its own approval; a second exchange of an item already exchanged; a print order without its required `Idempotency-Key`; a performed order's key reused with another body.

The model: each operation's request and channel, who may approve it (Ops 3: the same agent and User signed in to its account, or only its own Session when returned signed out), every revision fixed once returned, which were declined, whether only the User may approve, whether it was performed and its first response, and how many approvals reached it. Through `GET /state` it holds the Company to the same operations, revisions and approvals, and to the number of actions performed (at most once, Ops 7).

### `test_handoff_direct.py`: handoff and Direct Conversations

On top of the conversation rules: hand off (202 `{conversation_id}`, `handoff: pending`, responder `agent`); cancel a handoff (202, `handoff: none`); a person joins (`human`, nothing pending); no one is available (back to `none` with `agent`, and the Company Agent says so, 8.9); the Company closes a conversation; the Company asks for the User (`user_requested`); a retry of a handoff, cancel or close gets the original response; open a Direct Conversation from any conversation and any Session, with the outcome 8.10 gives (`conversation_not_found` for another User's parent, `invalid_request` for a Direct Conversation as parent, a challenge signed out of the parent's account, `conversation_closed`, `direct_conversation_open` naming the open one, or 201); accept a `user_requested` invitation with `parent_conversation_id` and `user_requested_event_id`, with or without a message, and again in a new request (the same Direct Conversation); a message or handoff to a parent while its Direct Conversation is open (`direct_conversation_open`). Reject rules: a handoff or cancel to a closed conversation (`conversation_closed`); a handoff's id reused on another path (`request_id_conflict`); an invitation naming an event that isn't a `user_requested` in that parent (`invalid_request`); by our reading of S12, the agent's own words opening or sent into a Direct Conversation, accepted and recorded. Reads use pages of 1 to 20 events.

### `test_mcp_browsing.py`: MCP, the browser join and website pages

MCP (7): every request carries the Session header with the Session's version and extensions and, signed in, a token for the server's `url` from the refresh token with `resource` (RFC 8707), asked for again when the Session's sign-in changes. Each example's mock speaks MCP 2025-06-18, 2026-07-28 or both (`mcpVersions`). The client learns which with a 2026-07-28 `server/discover` probe, falling back on the binding's legacy signal, written from the MCP 2026-07-28 text. Under 2026-07-28 each request carries the protocol fields in `_meta` and its mirrored headers (`Mcp-Name`, `Mcp-Param-*` for `x-mcp-header` arguments, Base64 when needed) and no `Mcp-Session-Id`; under 2025-06-18, `initialize` and the session. Then `tools/list` and `tools/call`; the exchange tool needs `orders:write` (signed out, a Bearer challenge naming the scope and the server's metadata; short of it, `insufficient_scope`; with it, an operation with its `terms`); the server's protected resource metadata names it and the issuer. Reject rules: the Company's default token at the MCP server; the MCP server's token at the OpenAPI API; `Mcp-Session-Id` on a 2026-07-28 request; an `Mcp-Name` that differs from the body; `initialize` at a server that speaks only 2026-07-28; a 2025-06-18 request outside its session.

The browser join (6): each run draws a Company with a browser join, without one, with `web.disabled` (no browser join), and with or without `web.unscoped`. The Personal Agent's own browser loads the join page (not cached, not framed, a `__Host-` cookie that is Secure and SameSite Strict), our request authorizes its code at `{endpoint}/authorize` (204) with the access token only when it has `poppy:browser-sign-in`, and signed out otherwise; a token without the scope is refused with `insufficient_scope` naming it, and the same code is then authorized signed out; the browser submits the code alone (303, the Session's cookie Secure and HttpOnly); then the website acts for the account and scopes the join authorized until that sign-in is revoked, and never for an ended Session. Where no browser join is listed, the agent fetches pages of `organization.domain` with its own client, with the Session header and no token, and they are signed out. Reject rules: the code submitted before it was authorized, twice, or from another browser; authorized twice, or as a form; an access token with a page (`invalid_session`, as its JWT has `ath`); a page without `Poppy-Version`; the Session header on a page of another host; a form posted to a `web.disabled` website (403); asking for `poppy:browser-sign-in` from a Company with no browser join (`invalid_scope`).

### `test_limits_device.py`: rate limits and Device Sign-In polling

Rate limits (5.6): the `rate_limit` hook makes the next n token or resource requests 429. An invariant replays the Company's limiter over every request the client sent and holds each answer to it: which got 429, each with the `Retry-After` it should carry. The honest rules carry on through the limits. Reject rules: the same request again inside its `Retry-After` (429, the MUST, recorded), and a different request inside another's (429, the Guides' advice, recorded as a warning).

Device Sign-In (4.3): start (the codes, `verification_uri`, `expires_in`, `interval`); the User approves (some or all scopes, for an account) or declines, at once or between polls; time passes; poll every `interval` (`authorization_pending`, `access_denied`, `expired_token`, or the tokens, which go to a Session as any sign-in's do). Reject rules: polling sooner than `interval` (`slow_down`, and 5 s more for every later poll; too soon again is recorded, RFC 8628 3.5); polling after the final answer (recorded).

## What the 0.4 port changed

Rules adapted to 0.4: discovery's `excluded_tasks.url` document and top-level `feedback.endpoint` became `tasks.endpoint` and its response (9); client metadata `extensions` became `Poppy-Extensions` on each request (3.4); message ids became request ids, and `message_id_conflict` became `request_id_conflict`; 0.3's `status` (`idle`, `queued`, ...) became `handoff`, `responder`, `closed` and `working`; handoff and close answer 202 with `{conversation_id}`, close also on a closed conversation; `extension_required` moved from `WWW-Authenticate` to a JSON body; Operations 2's `summary` became the required `terms`, and approvals gained `approver`, `approved_at`, `input_type` and `reference`; the honest browser join no longer sends a token without `poppy:browser-sign-in`.

No rule was dropped outright; each 0.3 rule has a 0.4 form. The checks with no 0.4 equivalent went: 0.3's `status` values and `queued` (the model's `check_status`), close answering 200, a message carrying its own `id`, `extension_required` in `WWW-Authenticate`, a token with the browser join whatever its scopes, and discovery that refused to follow a redirect of `poppy.json` (0.4's discovery follows redirects to HTTPS URLs; documents it links are still fetched without one).

## Bounds

For cost, not to dodge failures: reads never ask for `wait`, and retries don't either, since a long poll with nothing new holds each step for up to the mock's 2 s cap; a new conversation or a send asks for `wait` (0 or 1) only where its own message is already there to return. JSON integers stay within ±(2^53 − 1), RFC 8259's interoperable range. A device poll the rule means to be too soon stays 300 ms short of the interval, because the mock allows 250 ms of jitter.

`machine.WarmUp` starts the operations, MCP and rate-limit machines with up to three Users and up to four sign-ins, drawn as the `sign_in` rule draws them, so states such as two Users in one account are reached within the steps.

Not covered: an operation's `expires_at` passing (the mock times it on the real clock, ten minutes on); website operations (`webOperations`, Ops 4's operations endpoint) and Browser Control; the mock's 0.3-to-0.4 linked versions (`linkedVersion`); `cursor_expired`; streams the Company closes early; the Direct Sign-In consent page and `deny_authorization`; the mock's knobs that model a Company departing from the text (`neverQueued`, `ignoreWait`, wrong issuers, redirects).

## What it found

**In the 0.4 port, 12 November.** The mock departed from the 11 November text in these places, all fixed the same day. Each case but MOCK-4 is a regression test in `test_findings.py`, and in `test/mock-company.test.ts` under "the mock Company, as the Hypothesis model found it"; the machines now model each of those.

- **MOCK-1.** The mock recorded a handoff, cancel or close request id as accepted, and as the conversation's latest request, before it checked `conversation_closed` and `direct_conversation_open`. A refused handoff sent again got 202, and a later Company Agent message could name the refused request in `as_of_request`. 8.3: "If the Company has already accepted a request with that ID, path, and body, it returns the original response"; 8.4: `as_of_request` is "the ID of the latest message, handoff request, or handoff cancel from the Personal Agent that it took into account".
- **MOCK-2.** A handoff cancel to a parent whose Direct Conversation is open was accepted. 8.10: "messages, handoff requests, and handoff cancels to the parent return `direct_conversation_open`".
- **MOCK-3.** Handoff, cancel and close ignored `wait` and answered `{conversation_id}`. 8.3: the agent "adds the `wait` query parameter to any POST", and the Company then responds as a read.
- **MOCK-4.** The operations endpoint answered `invalid_request` to a signed-out Session of the same agent and User asking about an account's operation. Ops 4: such a Session "gets a challenge for an operation that belongs to an account, as in section 3". The port's agent saw it in the mock's code, not in a run, since the machines don't cover website operations; its regression test is only in `test/mock-company.test.ts`, under the mock's operations on its website.
- **MOCK-5.** `approval.declined-resent` was recorded per revision, not per approval, so the User's own approval of a revision whose agent approval was declined was recorded as the declined approval sent again. Ops 6: "MUST NOT send that approval again" and "MUST NOT approve a new revision for the same action without asking the User" (readings v04-agent-approval-again).
- **MOCK-6.** An invitation accepted without a message didn't keep its request id, and the request's hash for a Direct Conversation left out `user_requested_event_id`, so the id reused with another body was taken as new or as a retry. 8.3: `request_id_conflict` for "A request reused an ID that the Company accepted with a different path or body".
- **MOCK-7.** `version.changed-in-session` compared `Poppy-Extensions` as text, so the same RFC 9651 List written with a space after `;` was recorded as a change (3.4). The mock's parser also refused that space, which RFC 9651 3.1.2 allows, so such a Session declared no extensions at all.
- **MOCK-8.** With `webDisabled` and `browserSession` both set, `poppy.json` listed no browser join, as 6 requires, but the issuer still listed `poppy:browser-sign-in` and granted it, without recording `browser-sign-in.no-endpoint`. 6: "A Company that sets `web.disabled` MUST NOT list `browser_session_endpoint`" and "A Personal Agent requests `poppy:browser-sign-in` only from a Company that lists `browser_session_endpoint`".
- **MOCK-9.** With `webUnscoped`, `poppy.json` set `web.unscoped`, but the website still needed `orders:read` in the cookie's scopes to show orders. 3.1: `web.unscoped` is "`true` if the website doesn't apply the Company's other scopes, so `poppy:browser-sign-in` gives the account's full access there"; 6: such a website treats `poppy:browser-sign-in` "as access to everything the account can do on the website".

**During the 0.3 verification review, 29 October.** The official Company kit exposed the mock dropping message `context` from its events. The independent Python model had the same assumption: its oracle removed `context` before comparing a message with the event. The oracle now checks the whole message as sent. Three fixed counterexamples cover empty context, availability and locale/time-zone context, with context-only messages and negative controls for lost or changed values. These cases fail under the old oracle. [Verification assessment and evidence at the time](https://github.com/adewale/pda/blob/289c6592c6f6e629b1d525247f3c4e2243662bc2/docs/poppy-0.3-conformance.md#is-the-03-verification-sufficient).

**In the 0.3 port, 29 October.** Device Sign-In refused `addresses` with `invalid_scope`, though the issuer lists it in `scopes_supported`, which 4.7 says holds every scope a Personal Agent can request. The mock now leaves out a listed scope a sign-in type can't grant, as RFC 6749 3.3 allows, and refuses only an unlisted scope or a request with nothing left to grant. Writing the model showed a second slip: with `omitTokenScope`, the mock left `scope` out of the token response even when it granted less than was asked, which RFC 6749 5.1 forbids; it now names the scope whenever it differs. Both have regression tests in `test/mock-company.test.ts` under "the mock Company, as the Hypothesis model found it".

**With the 0.1 client, October.** The ledger is in `docs/history/spec-issues.md` (N4, S8, S9). Each was fixed in the mock and has a regression test in `test/mock-company.test.ts`:

- **Another User's operation** (Operations 1). A proposal of the jacket exchange returned the open operation of whichever User was signed in to the same account first. The mock now matches an operation only for the same agent and User.
- **A handoff while a person handles the conversation** set `queued` with `responder: human`; the text says that while a handoff is pending the responder stays `agent`. The mock now changes nothing: there's no one to find.
- **No `direct_closed` when the parent's close closed its Direct Conversation.** The mock now closes the Direct Conversation first, so the parent gets `direct_closed`, then its own `closed`.
- **Any request inside a `Retry-After` was the MUST**, though the text says "before sending *the request* again". The mock records `rate-limit.retry-after-ignored` only for the same request sent again, and a different request as `rate-limit.shared-limit-ignored`, a Guides warning.

Questions for the text's authors these models raised, not in `docs/poppy-0.3-issues.md`:

- **Handoff while a person is already handling the conversation** (8.9): a no-op, a new queue with `responder: agent`, or an error?
- **The parent's own close and `direct_closed`** (8.10, 8.12): does closing the parent add `direct_closed` to it, and before or after its `closed` state?
- **"The request again"** (5.6): only the request that got 429, or anything sent to that Company? It decides whether an agent that keeps one limiter per task, not per Company, is conformant.
