# Poppy implementations

Every public implementation of [Poppy, the Personal Agent Protocol](https://personalagentprotocol.org/) (Draft 0.1) we could find, surveyed on **11 October 2026** and again on **12 October 2026**, six days after Sierra and Meta announced it and three days after the draft was published. Everything listed is at most a few days old, so "last commit" is nearly always the survey's day. The whole ecosystem around them (the spec, checkers, demo Companies, adjacent projects, and how they work together) is mapped in [ecosystem.md](ecosystem.md).

**12 October.** We rechecked every row: new commits and releases, archived repositories, Sierra's GitHub organisation, the spec site (`node scripts/spec-snapshot.mjs`: no text changes), and the same GitHub, npm, PyPI, crates.io and web searches, for anything created since 5 October. We fetched no `poppy.json` that day. New hosts come from public directories, and say so. We read each new repository at a pinned commit, and ran two validators only in a container with no network ([the cross-check](interop-testing.md#validator-cross-check)).

**11 October method.** Read-only. GitHub search for repositories, code (`well-known/poppy`, `personalagentprotocol`, `poppy_domains`, `poppy:write`, `browser_session_endpoint`, `PoppyClient`, `poppy-client`, `poppy-agent`, "Personal Agent Protocol"), issues and pull requests created since 1 October; npm, PyPI and crates.io; web search; the two community lists ([awesome-poppy](https://github.com/JaviChulvi/awesome-poppy), [poppy.md/implementations](https://poppy.md/implementations)). One `GET /.well-known/poppy.json` per domain: a bare-domain redirect to `www.` was followed once. Documents that came back were checked offline with our validator (`npm run validate -- --kind poppy --domain <d> <file>`). That checks only the document itself, not the issuer's OAuth metadata. Nothing was posted, starred or forked.

## What we can learn from the 12 October participants

Each lesson names the change it suggests. None is made yet; the ones marked **decision** are the owner's.

1. **Say each message's basis.** poppy-validator gives every rule a basis (MUST, field table, advisory, context), and `--strict` fails only advisory findings. Our mock's checks already name theirs (`test/mock-company/violations.ts`); our validator's messages don't. Add a `basis` to each entry in `src/validator/messages.ts`, show it in the report and the CLI, and let `--strict` follow it.
2. **Check the host in every URL.** poppy-validator refuses `https://.` as `auth.issuer`; ours accepts it. `httpsUrl` in `src/validator/primitives.ts` should require a host name or an IP literal, with a fixture in `test/validator.test.ts`.
3. **Severity by declared version.** The draft says each API's `type` "MUST be one of" `openapi` and `mcp`, and that anyone else's extension MUST have a domain prefix. poppy-validator makes both errors in a 0.1 document and info in a newer minor, which may define them; we report info and a warning whatever the version. Pass the declared minor to `checkApis` and `checkExtensions` in `src/validator/profiles/draft-0.ts` and do the same.
4. **Don't be stricter than the text where it's cosmetic.** An integer extension `version` is an error for us and fine for them; the draft states no type ([N22](spec-issues.md#n22)). Make it a warning.
5. **Field-table members.** poppy-validator errors on an `apis` entry without `description`, an empty `agent.protocols` and a missing `organization.name`, reading the field table as required; we warn ([S18](spec-issues.md#s18)). **Decision:** follow the field table, or keep warning because agents work either way.
6. **A byte order mark.** RFC 8259 says senders MUST NOT add one; both Python validators fail to parse it, and we warn. **Decision:** make `json-bom` an error.
7. **Diagnose a misplaced metadata document.** When the issuer has a path and its metadata isn't at the RFC 8414 location, poppy-validator also tries the appended location and says it found it there (`OA09`), still failing the check. Our validator could do the same as a diagnostic, never our client ([S3](spec-issues.md#s3)).
8. **Keep the cross-check.** Their 51 fixtures (MIT) and ours, run through both validators, found one gap in ours and several readings. **Decision:** commit the cross-check as a small script beside `interop/vectors/datalayer/`, fetching their fixtures at a pinned commit and running their code only in Docker, or leave it as the one-off in [interop-testing.md](interop-testing.md#validator-cross-check).
9. **Move the Datalayer pin.** 0.10.0 accepts all three client assertion `aud`s, so adonis-agora's S1 failures at both Datalayer Companies should pass, and a known failure that no longer fails makes the run fail. **Decision:** bump `interop/registry.json` to `0c048aa`, rebuild the two Datalayer images, and update `interop/known-failures.json`.
10. **Path issuers are coming.** Fillthemat plans one issuer per School under a path on a shared host, with RFC 8414 insertion, which is what our `DP` scenario tests. It reads S1 as "exactly this School's token endpoint"; if it means that at the revocation endpoint too, it would refuse our assertions there. Add it to the S1 evidence when its code lands, and run `DP` against it.
11. **A store that needs Operations for every order.** print-with-poppy is signed-out only and requires Operations v1 to order, so an operation proposed in a signed-out Session ([N19](spec-issues.md#n19)) is its normal path. It is in the grid now, for D and S0; its Operations need a signed-out Operations scenario the harness doesn't have yet ([interop-testing.md](interop-testing.md#candidates-from-the-12-october-survey)).
12. **Watch the directories.** PAP Checker's directory listed three hosts we hadn't seen. Read it in each survey, without fetching the hosts ([ecosystem.md](ecosystem.md#how-to-update-this-map)).
