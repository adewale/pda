# Poppy 0.3: what has to change

Draft 0.3 of the Personal Agent Protocol appeared on [personalagentprotocol.org](https://personalagentprotocol.org/docs/0.3/spec) between 24 and 25 October 2026, alongside the published, frozen 0.2. This page says what it changes for a Personal Agent, which of our files each change lands in, and the order to do it in. It is a plan, not a record: **nothing of 0.3 is implemented**, and the ledger and evidence sections that [poppy-0.2-upgrade.md](poppy-0.2-upgrade.md) has will be written when it is. The text review, bugs and contradictions in 0.3 itself, is [spec-issues-0.3.md](spec-issues-0.3.md).

## Where things stand

- **0.2 is published and frozen** (24 October). Its text is identical to our 19 October pin ([`spec/draft-0.2-2026-10-19/`](../spec/draft-0.2-2026-10-19/README.md)) apart from the site's links becoming relative; we diffed the spec, guides, Operations and Extensions pages. The 0.2 pin, ledger and `npm run check:spec` stand as they are.
- **0.3 is "in progress"**: its changelog "grows until 0.3 is published", and every 0.x may break the one before. The site serves it at `/docs/0.3/…`, and `/docs/spec` now points there.
- **Upstream's repository hasn't caught up.** `main` is still `39b35bd`, our 0.2 pin, so there is no commit to import with `npm run spec:import`, no 0.3 kit schemas and no 0.3 Company validator. `npm run spec:drift` sees nothing, because it compares the repository, not the site.
- **The evidence for 0.3 is two site snapshots**, made with `node scripts/spec-snapshot.mjs --save`: [01:47 UTC](../spec/draft-0.3-retrieved-2026-10-25/README.md) and [06:13 UTC](../spec/draft-0.3-retrieved-2026-10-25T0613Z/README.md) on 25 October. In those four hours the changelog went from eighteen entries to twenty-three, the spec gained a section 8 and lost `sign_in_required`, and 120 lines of it changed. The table below is against the 06:13 text. Re-run the script before implementing anything; the pin for an implementation must be an upstream commit, as [upgrading.md](upgrading.md) requires.
- **Operations is still called v1 but has changed**: its 3.2 and 5.2 now say `insufficient_scope` where 0.2's said `sign_in_required` ([T36](spec-issues-0.3.md#t36)). The Extensions page is unchanged.
- **No live Company declares 0.3** that we know of. The four live 0.2 targets in [live-0.2-testing.md](live-0.2-testing.md) and every peer in [`interop/impls/`](../interop/impls/) speak 0.1 or 0.2.

"Breaking" is upstream's tag. Size is for a Personal Agent plus our mock, validator and tests: S is a day's work or less, M a few days, L a week or more. Line references are to the 01:47 snapshot's `pages/0.3-spec.md`.

Cross-cutting, outside any one entry:

- **Version plumbing.** `src/poppy/protocol-version.ts` gains `"0.3"`, its revision and, once upstream has one, its commit; `isDraft2` (12 calls, in 17 files with the other `"0.2"` checks) becomes a profile selection with three values, and Operations behaviour is chosen by the document's `protocol_version`, since its own `version` no longer says ([T36](spec-issues-0.3.md#t36)). Unknown 0.x stays refused. The validator gets a `draft-0.3` profile and `src/validator/levels.ts` its basis mapping; the interop runner, adapters and `known-failures.json` get a `0.3` lane; `interop/impls/pda-mock` registers 0.3 variants of `lenient-company` and `strict-company`, which are the only 0.3 Companies there will be until peers move.
- **The ledger.** `spec/requirements-0.3.json` with a disposition for each of the twenty-three entries, generated into this page by `npm run spec:docs`, and `scripts/check-spec.mjs` extended to a second pin. The pin needs an upstream commit; until there is one, the snapshot above is the citation and `check:spec` keeps verifying 0.2 alone.
- **The schema.** One additive migration to `poppy_sessions` (Session Key and thumbprint, `session_id` nullable); `test/rows.test.ts` checks the declarations. Rows from 0.1 and 0.2 Sessions keep working; a 0.3 Session is never resumed by an older binary, so [upgrading.md](upgrading.md)'s rollback note gains a line: stop 0.3 interactions before rolling back.
- **Docs.** `pda-spec.md` (the header's version statement and Appendix A, which cites section numbers that moved: section 5 is rewritten, 9.5 and 9.6 are new), `docs/capabilities.md`, `docs/readings.md` (the readings in [spec-issues-0.3.md](spec-issues-0.3.md) under "Our reading"), `spec/grounding.md` (quotes for every 0.3 requirement we claim), `docs/conformance-levels.md` if any basis changes, `docs/interop-spec.md` (a browser-join scenario, a Token Exchange scenario, a key-rotation-is-a-new-Session scenario), and the privacy policy if the Session Key changes what a Company can link (it doesn't: Sessions of one User are already linked by User ID).

## Order of work

The 0.2 upgrade's rule holds: change only the decisions 0.3 changes, reuse everything else, and never let a newer version fall back to an older profile. In this order, each step shippable behind the 0.3 profile with 0.1 and 0.2 untouched:

1. **Pin and profile.** Wait for, or ask upstream for, the 0.3 commit; import it; add the version, the profile skeleton and the ledger with every entry "Not started". Until then, the snapshot is the text and nothing in `src/` changes.
2. **Discovery and validator** (changes 1, 8, 9, 19, 21, 2's reserved prefix). Pure parsing and checks, fully testable against the mock and the snapshot's examples. The validator can ship 0.3 before the client does, as it did for 0.2.
3. **Session Keys and the token endpoint** (4, 12, 13, 17, 23). The large one, and everything after depends on it. Do the mock first, from the spec text, then the client, then the property model. Keep the 4.8 disambiguation ([T1](spec-issues-0.3.md#t1)) and the start-before-sign-in rule ([T2](spec-issues-0.3.md#t2)) as explicit readings.
4. **Scopes** (2, 10, 3, 6). Touches the model's tools and the cards, so it needs the page tests and a run-through in `docs/using.md`.
5. **Browser join** (5, 7's code handling). Mock first, then `browser.ts`; the `__Host-` prefix implies `Secure`, which the Hypothesis lane already satisfies by presenting `https://` URLs to the mock over 127.0.0.1.
6. **MCP Token Exchange** (14), **secrets tests** (7), **sign-out** (18).
7. **Interop lane, docs, Appendix A, changelog entry**, then a staging deploy against our own 0.3 mock. There is no live 0.3 Company to check against yet; say so in the changelog rather than counting the mock as one.

Don't start step 3 while the draft is moving under it unless the owner accepts rework: of the twenty-three entries, the Session Key design is the one most likely to shift after review, and it is the one the rest hang on.

## What 0.3 does to the 0.1 catalogue

Each of the 64 findings in [spec-issues.md](spec-issues.md) is graded against 0.2 and 0.3 in [spec-issues-0.3.md](spec-issues-0.3.md#the-01-catalogue-in-02-and-03). In 0.2, 16 are resolved, 14 partly and 34 open; in 0.3, 21 resolved, 14 partly, 28 open and one worse (N4, step-up revocation). Four of the five Critical findings are resolved; N10, which hosts may receive a Session Token, is not. Of the thirteen High findings, two are resolved, five partly and six open: N45, N43, N25, N5, S22 and S20. The readings in [readings.md](readings.md) for the open ones still apply to a 0.3 profile.

## Are we ready to implement 0.3?

Not properly, not yet. "Properly" here means what [upgrading.md](upgrading.md) asks of every version: a pinned upstream commit, a ledger entry for each change, the official checks, and evidence against someone else's implementation. On 25 October none of those is possible, and our own 0.2 isn't finished:

What can start now, without rework whatever the draft does next:

1. **Replace `isDraft2` with a profile selection**, and choose Operations behaviour by `protocol_version`. No behaviour changes; the 0.1 and 0.2 tests prove it.
2. **The discovery path rule** (row 21) for every version: one check, and it closes a real attack in 0.2 as well.
3. **Readings for T1, T2, T3 and T34** in [readings.md](readings.md), so the 0.3 work starts from written decisions.
4. **Close 0.2**: the signed-in live journey against a Company that has given us a test account, then promote the changelog entry.
5. **Ask the owner** whether to send T2, T1, T3, T34, T36 and T38 to the authors' issue tracker now, while the text is still moving.

Start the 0.3 profile itself (steps 2 to 7 of the order of work) when upstream has a 0.3 commit, or when the owner accepts rework against the site text.

## Open questions for the owner

- **When.** 0.3 is a moving draft with no published date, no upstream commit, no kit and no live Company; see the gates above. Implementing now buys early interop evidence and early feedback to the authors; waiting avoids rework on the Session Key design. The validator and discovery parts (step 2) are cheap and safe to do first either way.
- **Whether to keep 0.1.** The 0.2 upgrade kept 0.1 for the live Companies that still speak it. Three profiles cost more than two in every table and test; dropping 0.1 when 0.3 lands is the natural moment, if the live 0.1 targets have moved by then.
- **Sending the review.** [spec-issues-0.3.md](spec-issues-0.3.md) is written so each finding can go to the authors' issue tracker. T2, T1, T3 and T34 are the ones worth sending first, since a Company that reads the text another way than we do breaks sign-in; T36 and T38 next. T4 needs no report: upstream fixed it on 25 October. Nothing goes without approval ([SECURITY.md](../SECURITY.md)).
