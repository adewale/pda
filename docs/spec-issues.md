# Problems in the Personal Agent Protocol specification

Problems we found in [Personal Agent Protocol](https://personalagentprotocol.org/) (Poppy) Draft 0.1 ("Updated Oct 9, 2026"), its Guides and the Operations extension v1, written so they can go to the spec's authors. Each has a suggested fix and says what our client does meanwhile. [readings.md](readings.md) records, for the S-numbered questions, which reading our client and our strict and lenient mock Companies take, and why.

## How we found them

- **Building a client.** We built a Personal Agent client and a strict mock Company, which records a named violation for each check it makes (`test/mock-company/violations.ts`).
- **Running it under different readings.** Our conformance tests run under six readings of the questions below.
- **Reading other implementations.** We read the other implementations listed in [implementations.md](implementations.md); their issues are in [poppy-issues.md](poppy-issues.md). Their disagreements are often the evidence for an issue here.
- **A discovery-document validator** ([`src/validator/`](../src/validator)).
- **An interop grid.** Our [harness](interop-spec.md) runs agents against Companies from several projects, in containers, through a recording proxy; [a summary of the 11 October run](interop-results/README.md) is committed. Where two implementations that each pass alone fail together, the cause is usually one of the issues here, and the row says "Grid:".
- **A full crawl of the site on 11 October 2026.**
  - The sitemap lists nine pages: home, overview, spec, extensions, Operations, guides, open topics, license, contributions.
  - There's no `llms.txt`, changelog or public source repository; the only copy of the source is in poppyseed.
  - The home page's walkthrough traces exist only in a JavaScript bundle.
  - The spec has 107 sentences with RFC 2119 keywords, Operations has 20, and the Guides 138 bullet points, nearly all recommendations. Many more requirements carry no keyword, such as 4.4's "the Personal Agent starts a new Session" on `account_mismatch`. Which party each keyword sentence binds is a judgement; [spec/grounding.md](../spec/grounding.md#counts) lists them.
- **A snapshot of the site on 12 October 2026**, in [spec/draft-0.1-2026-10-09](../spec/draft-0.1-2026-10-09/README.md). Nothing had changed since 9 and 10 October, so since our crawl. [spec/grounding.md](../spec/grounding.md) quotes the text each issue below rests on and gives a verdict; issues the text partly addresses, or that we had misread, say so in their rows, dated 12 October.

**IDs.** S-numbers came from comparing implementations, N-numbers from the crawl and later work, including the grid. Our tests and docs cite them, so they don't change.

**Severity:**
- **Interop:** two conforming implementations can fail to work together.
- **Security:** a security or privacy risk.
- **Clarity:** underspecified, though implementations mostly agree.
- **Editorial:** examples or cross-references that contradict the text.

## Discovery and metadata (spec 3)

| ID | Severity | Problem | Suggested fix | What we do |
| --- | --- | --- | --- | --- |
| <a id="s3"></a>S3 | Interop | **Where metadata lives for an issuer with a path** (3.2). RFC 8414 inserts the well-known segment before the path; 3.2 cites RFC 8414, so insertion follows from it, but the draft only shows an issuer with no path. everruns appends; others insert. | Say "per RFC 8414 §3.1", with a path example. | [Our reading](readings.md#s3) |
| <a id="s7"></a>S7 | Interop | **Trailing slashes.** "Exactly" (3.2) makes `https://a.example` and `https://a.example/` different issuers. Datalayer's client strips the slash. | Keep exact comparison and say so, with this example. | [Our reading](readings.md#s7) |
| <a id="s18"></a>S18 | Clarity | **`web` has no URL** (3.1). `web: {}` and `apis: []` have no stated meaning, and `organization.name` isn't said to be required. Ilmer invents `web.url`. | Add `web.url`; say what empty means; mark `name` required. | The validator warns on a missing `name`. |
| <a id="n9"></a>N9 | Security | **Most URLs needn't be HTTPS.** Only `issuer` and conversation endpoints must be (#fields). These are open: `apis[].url`, `auth.mediated.endpoint` (which receives passwords), `web.browser_session_endpoint`, extension endpoints, and an operation's `url`. None has to be on the Company's hosts, and an off-domain operation `url` can't be a browser join's `return_to`. | Every URL MUST be HTTPS. The mediated endpoint MUST be on the issuer's host or `organization.domain`. | The validator requires HTTPS for every URL in `poppy.json`. |
| <a id="n24"></a>N24 | Editorial | **The metadata examples break RFC 8414.** They omit `response_types_supported`, which RFC 8414 §2 requires. They also don't show `authorization_response_iss_parameter_supported`, `dpop_signing_alg_values_supported` or `token_endpoint_auth_methods_supported`. | Complete the example. | The validator checks the latter three. |
| <a id="n26"></a>N26 | Clarity | **Extension endpoints and `auth`.** The rule for when `auth` is required (3.1) leaves out extension endpoints, which need Session Tokens. | Include them. | n/a |
| <a id="n27"></a>N27 | Clarity | **Subdomains.** `poppy.json` may be on a subdomain (3), but `organization.domain` must match the host requested, ignoring a leading `www.` (3.1). Nothing says how an agent finds `shop.example.com` from `example.com`, and `return_to` can't reach the apex. | Say how discovery reaches a subdomain. | Discover the host the User names. |
| <a id="n36"></a>N36 | Interop | **Issuer and origin.** The draft's own examples put the issuer on another host than the Company's domain: `poppy.json` for `example.com` names `https://auth.example.com` (3, 3.2), and the home page walkthrough does the same. *Corrected 12 Oct 2026: we had said the examples put it on the Company's host.* What the text doesn't say is whether the issuer may have a path (see S3), or be on a host outside `organization.domain`. Grid: poppy-demo's agent requires the issuer to equal the Company's origin, which contradicts the examples, so it fails every scenario at our mock (`auth.…`) and adonis-agora (`…/poppy`). | Say the issuer is any HTTPS URL the Company controls, with an example with a path (see S3). | Any issuer the document names, compared exactly. |
| <a id="n37"></a>N37 | Interop | **Redirects on OAuth endpoints, and how many.** *Corrected 12 Oct 2026: we had said the draft is silent on redirects at `/.well-known/poppy.json`.* It isn't: "The well-known URL MAY redirect … Personal Agents MUST follow redirects, and every redirect MUST be to an HTTPS URL" (3), and `organization.domain` matches the host requested, "After a redirect, the host the document is served from does not count" (3.1). The Guides add "a few redirects at most", and that Companies fetch `client_id` "without following redirects". Still open: no number of redirects, and nothing on redirects at the issuer's metadata or OAuth endpoints. withpoppyseed.dev 308-redirects the apex to `www.`, including its OAuth endpoints. An agent that doesn't follow a `poppy.json` redirect breaks a MUST. | State a maximum number of redirects for `poppy.json`; forbid redirects on the metadata, OAuth endpoints and `client_id`. | Follow up to three HTTPS redirects for `poppy.json`; none for `client_id`; compare `organization.domain` with the host named. |
| <a id="n44"></a>N44 | Security | **When to fetch `poppy.json` and API descriptions again.** The draft says to cache discovery documents by their HTTP caching headers (a SHOULD, 3 and 3.2) but never says when an agent must fetch and check them again: before every Session, before a sign-in, or only when the cache expires. *Partly addressed, noted 12 Oct 2026:* the Guides bound the cache, "at least a minute and at most a day", so a removed key stops being trusted; nothing makes the bound normative or says every fetch is validated again. A Company, or whoever takes over its hosting, can move an endpoint between discovery and a later call (a "rug pull"), and an agent that keeps using a document it validated earlier never sees the move, while one that re-fetches mid-task may see a document it has never checked. The same goes for an OpenAPI description's `servers` and an MCP server's protected resource metadata. | Say an agent MUST NOT use a document past its cache lifetime without fetching and validating it again, that every fetch is validated as discovery is (domain, issuer and token hosts), and make the Guides' maximum lifetime normative. | We cache `poppy.json`, the issuer's metadata and each OpenAPI description by their caching headers, bounded to between a minute and a day, and validate each fetch in full; within that lifetime a moved endpoint isn't seen. Our adversarial `XK` attack was dropped for this reason (see [adversarial-interop.md](adversarial-interop.md#malicious-company-scenarios)). |

## Agent identity and assertions (4.1, 4.2)

| ID | Severity | Problem | Suggested fix | What we do |
| --- | --- | --- | --- | --- |
| <a id="s1"></a>S1 | Interop | **The client assertion's `aud`** at the token, revocation and device endpoints is never stated. Implementations accept the exact endpoint, the token endpoint, or the issuer. Grid: adonis-agora's agent uses the token endpoint everywhere; poppyseed, poppy-demo, pi-poppy's Company and both Datalayer Companies require the endpoint called, so adonis-agora fails Device Sign-In and sign-out at poppyseed, pi-poppy and Datalayer. | Name it: the endpoint called. | [Our reading](readings.md#s1) |
| <a id="s2"></a>S2 | Interop | **Assertion `typ` and lifetime** are unspecified. Only browser assertions get "60 seconds"; the Guides say "reject assertions that claim a long lifetime" without a number, and recommend a `kid` on every key without saying a Company may require one. Strict Companies require `typ: "JWT"`, a `kid` and 60 s or less; others accept 300 s. Grid: pi-poppy's and adonis-agora's agents send no `typ`, so every signed-in or signed-out cell fails at a strict Company (our strict mock, poppy-demo's Northstar, Ilmer), and nothing past the first Session is tested. | State `typ`, `kid` and a maximum. | [Our reading](readings.md#s2) |
| <a id="n25"></a>N25 | Security | **Client and Session assertions can be confused.** Both are signed with the same keys and carry the same `iss` and `aud`; they differ only in `sub`. everruns doesn't check `sub == client_id`. | Give them distinct `typ` values, and require that check. | n/a |
| <a id="s6"></a>S6 | Clarity | **"Same domain"** for `jwks_uri` and `redirect_uris` (4.1) isn't defined: host, registrable domain, or port too? Redirects on the `client_id` fetch are covered only by the Guides ("Fetch the `client_id` URL without following redirects"), as a recommendation. *Corrected 12 Oct 2026: we had said redirects weren't addressed.* | Define it; make the Guides' no-redirect rule for `client_id` a MUST in 4.1. | Same host or parent/child host; a redirect is an error. |
| <a id="s21"></a>S21 | Clarity | **Local agents.** An HTTPS `client_id` on the same domain as the redirect URIs rules out an agent on someone's laptop unless it has a hosted identity. pi-poppy, poppyseed and Ilmer's tests use loopback `client_id`s. *Corrected 12 Oct 2026:* the Guides' "Native and distributed apps" already says what to do (keep the key on a server that signs for the app, return through an HTTPS app link, or use Device Sign-In); only 4.1 doesn't point to it. | Link the Guides' "Native and distributed apps" from 4.1. | Hosted identity. |
| <a id="n23"></a>N23 | Interop | **The client metadata example has no `grant_types`**, so RFC 7591's default (`authorization_code` only) applies, though the agent uses jwt-bearer, refresh_token and device_code. It also lacks `dpop_bound_access_tokens`. | Add both. | n/a |
| <a id="s19"></a>S19 | Interop | **Algorithms.** Is ES256 required, or only preferred? *Partly addressed, noted 12 Oct 2026:* the Guides say "Support ES256 and RS256, and sign with ES256 when you can", but the spec names no algorithm, so neither is mandatory to implement. withpoppyseed.dev advertises RS256 only, which departs from the Guides, not the spec. | Make ES256 mandatory to implement. | ES256. |
| <a id="n38"></a>N38 | Interop | **Key rotation: a new key, a new `kid`.** The Guides say "Give every key a `kid`" but not that a new key needs a new one. *Corrected 12 Oct 2026: we had said the Guides don't say whether a Company refetches on an unknown `kid` or how long it caches a JWKS.* They do: "Companies refetch `jwks_uri` when they see an unknown `kid`, with a rate limit", and cache "within bounds you set, such as at least a minute and at most a day". Grid: poppy-demo keeps `kid: agent-key-1` across rotations; pi-poppy's Company answers an unknown `kid` with `invalid_client` and doesn't refetch for 60 s, against the Guides; AuthKit caches for 30 s. An agent that rotates is refused for up to a minute. | A new key MUST have a new `kid`; make the Guides' refetch on an unknown `kid` normative. | Each key has its own `kid`; the old key stays published until its signatures expire. |

## Sessions and tokens (4.2, 4.3, 4.8)

| ID | Severity | Problem | Suggested fix | What we do |
| --- | --- | --- | --- | --- |
| <a id="s4"></a>S4 | Interop | **Signed-out `scope`.** "A signed-out token has none" (4.2) conflicts with Companies that gate conversations on `poppy:read`. 4.3 allows `scope` on any token request, yet three Companies reject it on the jwt-bearer grant. | Say what `scope` means there, or forbid it. | [Our reading](readings.md#s4) |
| <a id="n6"></a>N6 | Interop | **Required token response fields aren't listed.** `scope`, `session_id` and `signed_in` aren't marked required, and stock OAuth servers omit `scope` when it's unchanged. `"scope": ""` isn't valid RFC 6749 syntax. | List them; omit `scope` when it's empty. | A missing `scope` is taken as the scope requested (RFC 6749 §5.1), or as the scope already held when none was requested. |
| <a id="s5"></a>S5 | Interop | **Renewing a signed-in Session with an assertion** has no defined error. Companies keep it signed in, silently sign it out, or return `invalid_grant`. | Define the error. | Renew with the Account Token. |
| <a id="n4"></a>N4 | Interop | **Step-up revocation signs out parallel Sessions.** 4.4 says the agent SHOULD revoke the replaced Account Token; 4.9 says revoking signs out every Session signed in with it, perhaps including the one just stepped up. Rotation raises the same question, and so do two sign-ins to one account: is a Session signed in "with" a token, with the sign-in it rotated from, or with the account? Our own mock took the widest reading, signing out every Session of the account, until the Hypothesis model (`test/hypothesis`) caught it; it now signs out the Sessions signed in with that token or one it rotated from. | Sign Sessions in to the account grant, which outlives the token that started it, and say revoking one grant leaves others alone. | We revoke, as 4.4 recommends. The mock signs out the revoked grant's Sessions only. |
| <a id="n5"></a>N5 | Interop | **Rotation has no recovery.** If the response carrying a rotated token is lost, the retry reuses the old one, and a server following the OAuth security BCP revokes the whole family: the User is silently signed out. | A grace period for reuse, or idempotent retries. | We serialise token use per Company. |
| <a id="n28"></a>N28 | Clarity | **Account Token lifetime.** 4.4 gives `refresh_token_expires_in`, but the Guides say to expire unused tokens sooner, which the agent can't see. | Signal idle expiry. | Treat `invalid_grant` as signed out. |
| <a id="s14"></a>S14 | Interop | **DPoP error status at resource servers** (400 or 401?) isn't stated. *Partly addressed, noted 12 Oct 2026:* 4.3 says failed checks return `invalid_dpop_proof` or `use_dpop_nonce` "with the `WWW-Authenticate: DPoP` header" (no keyword), and the Guides' example answers `use_dpop_nonce` at an API with 401, as RFC 9449 does; the status of `invalid_dpop_proof` at a resource is left open, and 4.2's 400 is the token endpoint's. Companies that send no `WWW-Authenticate` depart from 4.3's text. | State 401 at resources, as RFC 9449 does, and make the header a MUST. | Read the header, then the body. |
| <a id="n1"></a>N1 | Interop | **DPoP at the device and revocation endpoints.** "A new proof for every request, including token requests" (#sending-tokens), but the device and sign-out examples carry none, and RFC 9449 doesn't define proofs there. | Proofs only at the token endpoint and resources; Companies MUST ignore them elsewhere. | n/a |
| <a id="s23"></a>S23 | Interop | **Nonces "for that server"** (Guides): per origin, or per Company? | Say per origin. | [Our reading](readings.md#s23) |
| <a id="n35"></a>N35 | Clarity | **One DPoP key per User?** 4.3 says the agent "generates a key pair for each User at each Company", with no keyword, and nothing says whether a Company may refuse a key it has already bound for another User. *Partly addressed, noted 12 Oct 2026:* the Guides recommend it, "Generate a DPoP key pair for each user at each company", which is a SHOULD in the Guides' sense. | Say SHOULD or MUST in 4.3, and what a Company does with a shared key. | A key per User per issuer. The mock records a shared key but still issues the token. |
| <a id="n39"></a>N39 | Interop | **The error for an ended Session at a resource.** *Partly addressed, noted 12 Oct 2026:* 4.2 does say where for renewal, "If it has ended, the Company returns `invalid_session`, and the Personal Agent starts a new Session", and lists `invalid_session` in the token endpoint's errors. What a resource returns for an ended Session is undefined: section 6 lists only `invalid_token`, `sign_in_required` and `insufficient_scope` (S13). Grid: Datalayer answers an ended Session with `invalid_token` everywhere, including the token endpoint, against 4.2; pi-poppy's agent renews on `invalid_token`, gets `invalid_session` from the token endpoint, and gives up instead of starting a new Session, also against 4.2. | `invalid_session` at resources too. | Start a new Session on `invalid_session` from either; renew on `invalid_token` at a resource. |

## Sign-in (4.4 to 4.9)

| ID | Severity | Problem | Suggested fix | What we do |
| --- | --- | --- | --- | --- |
| <a id="n2"></a>N2 | Security | **Sign-in isn't bound until the exchange.** `session_id` appears only when the code is exchanged or the device code polled, and the Company checks only the `client_id`, not the User ID. A code can be redeemed into another User's Session of the same agent, and the Account Token records the wrong User. A missing `session_id` is undefined. | Bind `session_id` at the start (authorization or device request, or PAR); check the User ID; define the error. | `state` is single-use, and the code is exchanged into the Session that started the sign-in. |
| <a id="n3"></a>N3 | Interop | **A different account at sign-in.** If the User picks another account during 4.5 to 4.7, the code is already spent, and it's undefined whether an Account Token is issued. There's no account hint. | Issue the Account Token with a new `session_id`. | Start a new Session on `account_mismatch`. |
| <a id="s16"></a>S16 | Clarity | **Approving zero scopes:** signed in with `scope: ""`, or `access_denied`? *Partly addressed, noted 12 Oct 2026:* 4.5 and 4.6 let the User approve "some or all of them, or decline", which implies approving none is declining, but nothing says so, and Mediated Sign-In has no approval step. | `access_denied`. | n/a |
| <a id="n7"></a>N7 | Interop | **Mediated Sign-In's wire contract is incomplete.** Undefined: HTTP status for `failed`, `expired` and `code_required`; the error format for `invalid_scope` (it isn't OAuth here); errors for a missing field, an unknown `sign_in_id`, another Session or an account mismatch; `expires_at` on the first step. (`refresh_token_expires_in` is covered: `complete` has "the same fields as the response in 4.4".) | Define them. | Handle the documented shapes. |
| <a id="n8"></a>N8 | Security | **Mediated Sign-In has no consent step.** No Company page is shown, and nothing requires the agent to get the User's agreement to the scopes. *Partly addressed, noted 12 Oct 2026:* the Guides already recommend the Company side, "Tell the user, for example by email, when a personal agent signs in." | The agent MUST get consent; make the Guides' notification a SHOULD in 4.7. | The User enters credentials on our card, which names the scopes. |
| <a id="n14"></a>N14 | Security | **Phishing on consent.** The consent page shows "the name and logo from its metadata document", which the agent chooses itself; only the Guides add the `client_id` domain. Ops 5.1 shows the Company's self-declared name. | MUST show the `client_id` host, and the Company's domain. | Our cards show the Company's verified `organization.domain` under its name. The consent page is the Company's. |
| <a id="n32"></a>N32 | Editorial | **`iss` on redirects.** The Guides say "Return `iss` in every redirect, success or error (MUST, 4.5)", but 4.5 says it only for success and `access_denied`. | Align them. | We require `iss` on every redirect, and it must equal the issuer. |
| <a id="n45"></a>N45 | Security | **A lost code-exchange answer orphans an Account Token.** If the answer to the code exchange (4.5), or the device-code poll that succeeds (4.6), is lost (a timeout, a dropped connection, a 5xx from a proxy after the Company acted), the Company has signed the Session in and issued an Account Token the agent never received. The code is single-use, so it can't be exchanged again; the agent can't renew that Session, because renewing a signed-in Session needs the Account Token (and S5 leaves an assertion's answer undefined); and it can't revoke the token, because revocation needs the token. The grant stays live until it expires, and the User sees an account connected to an agent that doesn't hold it. The draft has no idempotent exchange and no recovery. See also N5. | Let a retried exchange with the same code, verifier and `session_id` return the same answer for a short window, or let an agent revoke by `session_id` with its client assertion; say a Company ends the Session's grant when that happens. | We abandon that Session (it is never renewed with the assertion) and start a new one; the card says the sign-in was interrupted, and the User signs in again. The orphaned grant is left to expire at the Company. |

## Web browsing (5)

| ID | Severity | Problem | Suggested fix | What we do |
| --- | --- | --- | --- | --- |
| <a id="n13"></a>N13 | Security | **The browser cookie is a bearer credential.** It isn't bound to a key, lives as long as the Session, and may be `SameSite=None`, so other pages in the agent's browser send it cross-site. `Lax` is enough for the POST, 303 and GET. | Require `Lax`; recommend short lifetimes. | One browser context per Session of each User, replaced with the Session; cookies host-only and sent only to that host, and no other site's pages load in it. |
| <a id="n43"></a>N43 | Security | **Website actions outside Operations have no approval step.** Once the agent's browser joins the Session (5) it can submit any form on the Company's website (place an order, change an address, cancel a plan), and nothing in section 5 says which submissions are consequential or that the User must approve them. An agent that gates API writes can be routed around through the website, and a Company can't tell an approved submission from an unapproved one. *Partly addressed, noted 12 Oct 2026:* a Company can already route a website action through Operations (Ops 1, "an API call, an MCP tool, a conversation, or a web page"), and Ops 4.4 says that when the website confirms an operation "the Personal Agent's duties in 5.1 apply however it confirms". | Say that a Personal Agent MUST get the User's approval before a website submission that a write through the Company's API would need approved, or let a Company mark forms (or URLs) as consequential. | Every form submission waits for the User's approval on a card listing exactly what will be sent, and exactly that is sent; `click` follows links only, so it can't submit a form. |

## APIs (6)

| ID | Severity | Problem | Suggested fix | What we do |
| --- | --- | --- | --- | --- |
| <a id="n10"></a>N10 | Security | **Which hosts may receive Session Tokens** is undefined. "One DPoP Session Token works at all of a Company's services" (4.3), but an OpenAPI description's `servers` can name any host, and its `securitySchemes` can conflict with Poppy's DPoP rule. | Send tokens only to hosts listed in `poppy.json`, or under `organization.domain` or `poppy_domains`. | We send only to hosts `poppy.json` lists, or under `organization.domain` or a `poppy_domains` entry, and refuse a description whose server is elsewhere. |
| <a id="n17"></a>N17 | Security | **Bearer issuance isn't normative.** Companies must accept Bearer only at MCP servers, but nothing says the token endpoint MUST issue Bearer only for a listed MCP `url`. poppyseed treats any `resource` as a Bearer request, a downgrade. | Require it. | We ask for Bearer only for MCP. |
| <a id="n18"></a>N18 | Clarity | **MCP clients that don't implement Poppy.** Their sign-in "starts a new signed-in Session" with no User ID or `session_id`, and it's unclear whether their refresh tokens are Account Tokens. | Define it. | n/a |
| <a id="s13"></a>S13 | Interop | **API errors for an ended Session.** Section 6 lists only three errors; poppy-demo returns 400 `invalid_session` with no `WWW-Authenticate`. | Add `invalid_session`, or require `invalid_token`. | Start a new Session on either. |
| <a id="s22"></a>S22 | Interop | **Which writes propose operations.** A Company may use operations "for some actions and not others" (Ops 1). *Partly addressed, noted 12 Oct 2026:* Ops 4.1 says a Company SHOULD say in its OpenAPI description which endpoints return operations, but defines no marker (poppyseed uses `x-poppy-operation: true`) and says nothing for MCP tools or conversations. | Standardise a marker for OpenAPI and MCP. | Expect a proposal from any write at a Company with operations. |

## Conversations (7)

| ID | Severity | Problem | Suggested fix | What we do |
| --- | --- | --- | --- | --- |
| <a id="n16"></a>N16 | Interop | **Sign-out vs open conversations.** 4.9: "an open conversation carries on" signed out. 7.11: the same User signed out gets `sign_in_required`. 7.13: another account gets `conversation_not_found`. The Guides: close conversations that used the account. 7.11 can be read as narrowing 4.9; the Guides' close is what an agent can't predict, since a closed conversation answers `conversation_closed`. | Pick one. | Follow whichever error comes back. |
| <a id="s8"></a>S8 | Security | **Retries after sign-out.** 7.3 returns "the original response" to a retry; 7.11 requires sign-in. poppy-demo returns the original, which can include account data. So did our mock, for a retried first message, until the Hypothesis model (`test/hypothesis`) caught it. | 7.11 wins. | The mock answers 7.11 first. |
| <a id="s9"></a>S9 | Interop | **Message-id idempotency.** *Partly addressed, noted 12 Oct 2026:* 7.3 answers "per conversation?": ids are unique "for the User rather than for one conversation", so a retried first message sent to `POST {endpoint}` returns "the conversation it already started". Still open: a retry while the first is in flight; what "the original response" includes; and whether a retry of a conversation's first message may go to `{id}/messages` of the conversation it started, instead of starting it again. ## Open topics, with our view

- **Payments.** Ops already covers approval. A payment extension could sit on Ops, with amounts in a standard `{amount: string, currency}`, which would also fix S20 and N33.
- **Push notifications.** We poll every 30 seconds to 15 minutes. Suggest a `notification_uri` in client metadata, receiving signed, content-free "events available" pings, after which the agent reads with its cursor.
- **Attachments.** HTTPS URLs on the Company's hosts, fetched with DPoP, with a declared type and size. Forms go through Ops or `url`.
- **Missing from the list:**
  - version negotiation (N22);
  - a security considerations section (N15);
  - resetting a User ID (N12);
  - a shared conformance suite (see [interop-testing.md](interop-testing.md));
  - delegation, such as family accounts.
