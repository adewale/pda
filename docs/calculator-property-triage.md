# Calculator property: error precedence

On 21 October 2026 the full test run generated `(0) / ((0) * ((1e590)^3))`. The independent fraction reference marked its final value as division by zero. The property therefore required a `Division by zero` error, but the calculator returned `A number in the calculation is too large`.

This was an error in the property oracle. The [calculator contract](../pda-spec.md#general-tools) limits numbers to 4,000 bits. Its eager parser evaluates `(1e590)^3` before multiplying by zero or dividing. That intermediate requires about 5,880 bits, so rejecting it preserves the documented resource bound. Symbolically skipping the power or lifting the bound would change the calculator's evaluation and safety policy to satisfy an unwarranted error-precedence assumption.

The correction applies the existing size-refusal check to both reference outcomes: every refusal must be a `CalcError`; a division-by-zero error is valid only when the reference found division by zero; a size error still requires the independent reference's recorded largest intermediate to exceed 3,000 bits, exactly the existing threshold. That threshold already accommodates the calculator's conservative power precheck and reference intermediate reductions; this change does not loosen it. A successful result when the reference found division by zero still fails. Exact result and rounding assertions and all generator domains remain unchanged.

The deterministic regression covers the generated expression, the oversized power multiplied by zero without division, an analogous in-bounds power that must still report division by zero, and a division by zero evaluated before an oversized right operand. The original behavior was reproduced directly before changing the property. No calculator implementation was changed.

Hegel review: the affected public surface is `calculate(expression)`, including successful exact arithmetic and named resource/domain refusals. Its exported limits and `CalcError` have no sibling evaluator; the existing properties for parsing, money, rounding, approximate arithmetic and clock tools remain untouched. The correction preserves full generated domains, an independent arithmetic oracle, exact comparisons, both acceptance and rejection, and the default case count. The four fixed cases are ordinary regression tests, not properties disguised with fixed generators.
