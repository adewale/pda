# Poppy 1.0: the upgrade

PDA speaks the 1.0 draft beside 0.4 since 13 November ([decision 51](decisions.md#51-10-beside-04)). 1.0 is pinned from the [13 November 2026 snapshot](../spec/draft-1.0-retrieved-2026-11-13/README.md), retrieved at 15:48 UTC, and the [official kit](../spec/company-kit-2026-11-13/README.md) downloaded the same afternoon, both at upstream commit `bb98332`. They replaced a snapshot and kit from that morning (`736ef95`) before either was merged, since upstream added ten changelog entries in between. 1.0 is a draft, so a newer snapshot replaces this pin after review ([upgrading](upgrading.md)); 0.4 stays frozen at its [11 November pin](poppy-0.4-upgrade.md).

## What changes between 0.4 and 1.0

Extensions keep their versions: Operations 3 and Mediated Sign-In 1. Of the six breaking changes, three ask something new of the agent, one is the Company's alone, one concerns UCP, which PDA doesn't speak, and one changes only what a 1.0 document must contain:

- **Conversation protocol descriptions** (8.1) apply to 1.0 alone. The [1.0 validator profile](../src/validator/profiles/draft-1.0.ts) is 0.4's with a required `description` on each `agent.protocols` entry, and discovery refuses a 1.0 Company without one. The model reads the description in `poppy_discover`.
- **Pushed Authorization Requests** (4.2) apply under both versions, because RFC 9126 defines the metadata for any client ([reading](readings.md#pushed-authorization)). When the issuer lists `pushed_authorization_request_endpoint`, the Direct Sign-In card links to the agent's `/poppy/sign-in` page, which pushes the request with the client assertion and a DPoP proof each time the User opens it, then redirects to the authorization endpoint with only `client_id` and `request_uri`.
- **Consent for scopes granted before** (4.2, 10.8) applies to 1.0 alone: every Direct Sign-In request to a 1.x Company carries `prompt=consent` ([reading](readings.md#v10-prompt-consent)).
- **The same DPoP key at refresh** (4.4) applies under both versions, since 0.4 allows keeping a key. Keys by issuer and User ID are sealed in `poppy_dpop_keys`, so a restart refreshes with the key the refresh token was issued with, and each server's latest nonce is kept in `poppy_dpop_nonces` for the key to keep sending ([reading](readings.md#v10-dpop-key)).
- **PS384 required** is a Company obligation. The agent signs with ES256, which every Company must accept. The 1.0 validator profile reports an issuer whose listed client-assertion algorithms leave out ES256 or PS384.
- **UCP scope requests name every scope** concerns UCP, which PDA doesn't speak. Its general sign-in already requests every scope still needed (4.7).

Of the minor changes, conversations gained room to extend ([reading](readings.md#v10-extend)): a message with a `role` the agent doesn't know is the Company's content, and in a 1.x conversation a stream event with an SSE name it doesn't know is skipped. The 1.0 validator accepts a port other than 443 in `organization.domain`, though the agent uses no Company on another port. Under 1.x the mock takes a `context` field set to `null` as cleared.

Choosing a version follows 3.4 ([reading](readings.md#v10-choice)). From 1.0, a newer minor version is compatible: a Company serving 1.1 is used as 1.0, and every request declares `Poppy-Version: 1.0`, the version the agent implements. The validator checks such a document with its 1.0 profile and notes the newer version (`version-newer-minor`).

## How it is checked

- **The mock** serves 1.0, 1.1 or 0.4, alone or with a linked document, describes its protocols under 1.x, can offer or require PAR (`pushedAuthorization`), bind refresh tokens to their key (`bindRefreshTokens`), and stream an event a later version might add (`laterStreamEvent`). Its new checks are `authorize.prompt-consent`, `par.not-pushed`, `par.extra-parameters`, `par.code-key` and `dpop.refresh-key-changed`, each with a negative `TAMPERS` case.
- **The agent against the mock**: [test/poppy-1.0.test.ts](../test/poppy-1.0.test.ts) covers the version choice and declaration, the description reaching the model, PAR (the card's link, a push with a proof on each opening, a full sign-in, a signed-out browser, an unknown id), `prompt=consent` under 1.0 and not 0.4, unknown roles and stream events, and refresh with the stored key after the agent's memory is lost. Every request is also checked against the schemas of the kit for the version it declared.
- **The kit against the mock**: `node scripts/check-company-kit.mjs --protocol 1.0 --reviewed-findings` gives the same results as the 0.4 kit ([reviewed findings](../test/company-kit/reviewed-findings-1.0.json)). The kit's validator checks none of the agent-side changes, so they rest on our own mock checks.
- **Not yet at 1.0**: the Hypothesis client and the interop harness still declare 0.4, so neither exercises 1.0. The mock Companies in the interop grid serve 0.4.
