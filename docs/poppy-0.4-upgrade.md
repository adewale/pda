# Poppy 0.4: the upgrade

PDA speaks 0.3 and 0.4. 0.4 is pinned from the [11 November 2026 snapshot](../spec/draft-0.4-retrieved-2026-11-11/README.md) and the [official kit](../spec/company-kit-2026-11-11/README.md) retrieved the same day, both at upstream commit `ed47408`. Upstream published 0.4 on 10 November as the 1.0 release candidate, so this pin is frozen: fixes before 1.0 go into a draft 1.0. [Decision 43](decisions.md#43-03-beside-04-both-versions-website-operations-and-approvals-across-sessions) records the choices this plan follows: support both versions, start on this draft, adopt website operations, bind approvals to the agent, User ID and account rather than one Session, and require an exact `resource` in protected resource metadata on both the derived and the challenge path.

The 10 November pin replaced the 9 November one (`b2569c5`) a day later. Upstream had added four changelog entries: Operations version 3 with agent approvals and required `terms`, the Browser Control extension, and the Session header on website pages fetched without a browser. Decision 43 expected Operations to stay at version 2 in both protocol versions. Under 0.4 it is now version 3, and 0.3 keeps version 2 (O3). [Decision 44](decisions.md#44-operations-3-with-agent-approvals-a-real-browser-and-the-fetch-browser-under-04) records the owner's choices on what the 10 November text added: agent approvals on the User's standing instructions, a real browser for Browser Control, the fetch browser counting as a browser only where it can join, and read-only fetching on a `web.disabled` website.

The 11 November pin replaced the 10 November one (`a2f16ec`), and with it the draft: upstream published the text as 0.4, the 1.0 release candidate, with six more changelog entries. A Company can decline an approval (`approval_declined`), and after a decline, or after a Company answers an agent approval with a new revision, only the User approves the action again. Direct Sign-In opened on another device is named as a cross-device risk (10.8). The protected resource metadata may list `scopes_supported`. The browser-session endpoint may be on another host. The guides cover scopes a Company doesn't grant and passkeys on consent pages. **V3** below records what each changed here.

0.3 and now 0.4 are frozen, so their pins, ledgers and kits stay as they are. Earlier 0.4 snapshots got newer ones. Each one gets its own dated directory, a review of the changelog and the diff against this pin, and an updated [ledger](../spec/requirements-0.4.json); work items below then move with it. [upgrading.md](upgrading.md) has the procedure.

## How the kit grounds the work

The kit is written for Companies, so it checks our mock Company directly and our agent indirectly. We use it three ways:

1. **The mock, milestone by milestone.** `node scripts/check-company-kit.mjs --protocol 0.4 --output <file>` runs the pinned, unmodified kit CLI against the mock over local HTTPS, with the mock declaring 0.4. Each mock item below names the catalogue checks it should turn from skip or fail to pass. Its expected findings are in [reviewed-findings-0.4.json](../test/company-kit/reviewed-findings-0.4.json), and CI runs it with `--reviewed-findings` beside the 0.3 kit (both now name `--protocol`, since the default is the newest runtime pin). Since C1, C3 and C4 the only findings are the 0.3 kit's DPoP prerequisite ones. Since T1 and the mock half of T2, the only mock skips are the two version checks; the mock returns a feedback alternative, which clears `feedback.alternative-references` in both kits. The reviewed run serves 0.4 alone ([reading](readings.md#v04-version-missing)).
2. **What the agent sends.** The kit's `schemas/` describe requests from a Personal Agent: conversation requests and messages, the Session JWT, the delegation, client metadata, approvals, feedback reports and the browser-session authorization. Tests that capture the agent's requests at the mock check their bodies against these schemas with the kit's own dependency-free `validate/schema.ts`, so neither our mock nor our validator judges our agent alone.
3. **Our validator against theirs.** The kit's `check --file <poppy.json>` checks a document offline. The validator's 0.4 profile (F7) is compared with it on the same fixtures; where they disagree, the pinned text decides and the reading goes in [readings.md](readings.md).

The kit can't check sign-in beyond an unknown `sign_in_id`, and it checks website operations and the Session header on fetched website pages not at all; those keep our own mock checks and interop.

**Baseline, 9 and 10 November.** Before any 0.4 work, both 0.4 kits stop at `discovery.schema` on all four mock profiles: 11 checks pass, 1 fails and 120 are skipped. The mock lists each extension as an object, and 0.4 lists the versions it serves (3.3). The mock performed nothing (`companyEffects` 0). F1 and M1 are the first items that move this.

## Order of work

Each item that changes the agent ships with the mock behaviour it needs, a stable id in `test/mock-company/violations.ts` with a negative `TAMPERS` case, and tests that fail when the change is reverted. "0.4 only" means the 0.3 profile keeps 0.3's rule.

**Layer 0.**
- **H1. DPoP keys by issuer and User ID** (4.5). Today the key cache is keyed by issuer, which gives one key per User ID only because each issuer has one stored User ID. Valid 0.3; ships first. Test: the same issuer and User ID give the same key, another issuer or a changed User ID a new one.

**Layer 1.**
- **H2. Exact protected resource metadata** (4.5; RFC 9728 3.3). Use metadata only when its `resource` is exactly the identifier it was fetched for, both at the derived URL and at a `resource_metadata` URL from a challenge (decision 43). The MCP transport's fallback to the root `/.well-known/oauth-protected-resource` follows the same rule. Valid 0.3. Tests cover a parent resource, a difference in case or trailing slash, a query, that no token request names the wrong resource, and a negative interop fixture.
- **V0. The schema oracle.** Done. The mock keeps what the agent sent, decoded: JSON bodies, Session JWTs and delegations, `Poppy-Approval` and the client metadata, but no form bodies. After every test, [test/kit-schemas.ts](../test/kit-schemas.ts) checks them with the pinned kit's unmodified `validate/schema.ts` and `schemas/`, beside the violation check in `agent-helpers`. [test/kit-schemas.test.ts](../test/kit-schemas.test.ts) shows that each schema is applied and that a broken payload is refused. Each request is judged by the kit for the version its `Poppy-Version` declares (0.3 sends none), and the client metadata, which serves Companies of every version, by both kits.

**Layer 2.**
- **S3. Readings.** Done: [readings.md](readings.md#v04-choice) records the version choice, linked documents, the retry after `version_unsupported`, conversations after a version change, `as_of_request`, the fetch browser, `web.disabled`, agent approvals, `reference` and Browser Control.

**Layer 3.**
- **F1. Versions and discovery** (3.3, 3.4). Done: `discover()` chooses through the validator's `validateCompany` with the versions the agent speaks, so it reads `supported_versions` and never falls back to a version the Company doesn't list. A 0.4 Company's extensions are read from their version lists (Operations 3 with its `endpoint`, Mediated Sign-In 1), `tasks.endpoint` replaces `feedback` and `excluded_tasks`, and `web.disabled` and `web.unscoped` are kept; the tasks and operations endpoints join the protocol endpoints a model's API call can't reach. Discovery chooses 0.4 when the Company offers it ([test](../test/poppy-0.4-discovery.test.ts)). The kit checks named for F1, `discovery.schema`, `discovery.protocol-version`, `discovery.supported-versions` and `discovery.versions-same-company`, judge the mock, so they move with M1.
- **F4. Error codes.** Done: `version_unsupported`, `version_mismatch` and `request_id_conflict` are protocol codes. A message refused with `request_id_conflict` is reported as our bug, as `message_id_conflict` is; one refused with `version_mismatch` tells the model the conversation can't continue and leaves it open for reads ([reading](readings.md#v04-conversations)). The mock's `refuseMessages` gives either refusal until it serves 0.4 conversations. R1 handles `version_unsupported`.
- **F7. The validator's 0.4 profile.** Done: [draft-0.4.ts](../src/validator/profiles/draft-0.4.ts) checks extension version lists, `tasks`, `web.disabled` and `web.unscoped`, website operations and Browser Control with join, `poppy:browser-sign-in` in `scopes_supported`, and Direct Sign-In preferred. `validateCompany` chooses a version the way F1's agent will, from `supported_versions` on the same host without following redirects, and checks the linked document. Messages for rules kept from 0.3 link to the 0.4 pages. Compared on 10 November with the kit's `check --file`: both refuse 0.3's extension objects, numeric extension versions, and `web.disabled` with join or with nothing else. The kit's offline check doesn't report website operations or Browser Control without join, members moved to `tasks`, or `supported_versions` off the host; the pinned text requires each (Operations 2, Browser Control 3, spec 3.4 and 9), so we keep them.
- **K1. Mock sign-in** (Company obligations). Refresh with `auth.disabled` answers `invalid_grant`; Sessions are found by client_id, `sid` and User ID; a delegated key reused for another User ID is refused.
- **K2. `auth.scopes` first** (4.7), 0.4 only. 0.3 keeps OpenAPI descriptions first.
- **K3. Device Sign-In links** on the issuer's host or `organization.domain` only (4.3), 0.4 only: under 0.3 an issuer for several domains may put its device page on another protected resource's host. The test's domain doesn't come from the mock's `poppyDomains`.
- **O1. Operations details** (Operations 3 to 7). `approved_at` and `input_type`, revisions whose summary alone changed, and approving an earlier revision the User prefers.

**Layer 4.**
- **F2. Session headers** (3.4, 5.2). Done: every request with the Session header carries what its Session declared ([declaration.ts](../src/poppy/declaration.ts)): under 0.4, `Poppy-Version` and `Poppy-Extensions` with Operations 3 when the Company lists it, and Mediated Sign-In never, since its grant type identifies it (3.3); under 0.3, neither. `poppy_sessions.declared` fixes the values for the `sid`; a Company document that calls for others starts a new Session, keeping its account, before anything is sent. A Session stored before the column was a 0.3 Session. The client metadata keeps `extensions` for 0.3 Companies; 0.4 reads none there and its kit's schema allows the member. [The tests](../test/properties/session-declaration.test.ts) send through the client to the mock's Company read as 0.4; M1's mock checks the headers itself. Kit: `session.version-missing`, `session.version-unsupported`.
- **F5. Storage.** Done: each conversation keeps the protocol version and `Poppy-Extensions` it started in, and 0.4's `working` and `handoff` (8.7) beside `responder`. `status` stays the local marker both versions share: 0.3's own value, or under 0.4 `closed`, `working` or `idle`, derived from `closed` and `working` (C1). So the `poppy_conversations_open` index and the `status != 'closed'` queries need no rewrite, and the migration only adds columns: an older agent's open conversations stay open as 0.3 conversations, and `retireIncompatibleConversations` isn't involved. The `poppy_protocol_conversation_status` trigger also logs a change of `handoff`. Request IDs are stored with C2, which sends them ([test](../test/properties/upgrade.test.ts)).
- **M1. Mock foundation.** Done: the mock serves 0.4 in its own shape (extension version lists, Operations 3, no `feedback` or `excluded_tasks`, `poppy:browser-sign-in` with browser join), and with `linkedVersion` serves a second version from one domain through `supported_versions`. It checks `Poppy-Version` on every Session request: a request without one is 0.3, and a version it doesn't serve gets `version_unsupported`. It records `version.missing` and `version.unlisted` when the agent declares a version the Company never listed, and `version.changed-in-session` when a Session's declaration changes. [poppy-0.4.test.ts](../test/poppy-0.4.test.ts) has the agent choose 0.4 from all three arrangements. On 10 November the 0.4 kit against the mock gave 75 passes on the lenient and strict profiles, 83 on bearer and 54 issuerless. What remains is the DPoP prerequisite already reviewed for 0.3 and `conversations.start`, which waits for the mock's 0.4 conversations (C2). `reviewed-findings-0.4.json` and its CI step follow once that passes.
- **W2. `web.disabled` and `web.unscoped`** (6). Kit: `discovery.web-disabled`, `discovery.web-unscoped`. **`web.disabled` is done** ([reading](readings.md#v04-web-disabled)): pages are read, no form is filled or sent, and the model is pointed to the agent and APIs. `web.unscoped` is read by discovery and shown to the model and on the sign-in card before `poppy:browser-sign-in` is requested (W1).
- **X1. `extension_required` in a JSON body** at APIs (7), 0.4 only. **Done**: OpenAPI, MCP and protocol endpoints share one reading, and the mock's MCP server sends it too.
- **W4. The Session header on fetched website pages** (5.2, 5.6), 0.4 only: under 0.3 website pages never carry it. Per decision 44, the fetch browser is the agent's own HTTP client wherever the Company lists no `browser_session_endpoint`. There each page gets a signed-out Session header, never an access token, and only on `organization.domain`. A redirect is re-signed only while it stays on that host, and after `invalid_session` the page may be fetched once without the header. On a `web.disabled` website it reads and never submits a form. The mock verifies the header on its pages and records one sent off-host or with `ath`. **Done**: a form isn't sent again after `invalid_session`, and the Session is started before a signed page names it.

**Layer 5.**
- **O3. Operations version 3** (0.4 Operations 3, 5, 6). Done: 0.4 Sessions declare `operations` version 3 and 0.3 Sessions keep version 2 ([operations-v2.ts](../src/poppy/operations-v2.ts)). Each approval adds its statement as it is sent: `approver="user"`, `approved_at` from the moment the User's decision claimed the card, `input_type="tap"`, and the approval's ID as `reference`. That ID is derived per Company or random, so it is unique per approval and never reaches two Companies. Under version 3 an operation needs `terms` and may omit `summary`; the card then shows every value in `terms`, labelled by its path, and only the request is compared with them. The mock requires `approver`, refuses `input_type` with `agent`, checks `approved_at` and `reference`, and returns operations only to requests that declare version 3 ([TAMPERS](../test/mock-company.test.ts) rows `approval.*`). Tests: [poppy-0.4.test.ts](../test/poppy-0.4.test.ts) for APIs, MCP, conversations and a card without a summary; the kit's `approval.schema.json` through V0. Agent approvals stay with AG1 and AG2.
- **AG1. Standing instructions** (Operations 5; decision 44), 0.4 only. **Done** ([instructions.ts](../src/poppy/instructions.ts), [the Companies page](../src/ui/instructions.tsx)). The User writes instructions on the Companies page, each scoped to one Company and optionally one account, with conditions on `terms` values: an amount at most a limit in one currency, a value from a list, or an exact value. Instructions are stored as data the model can't write; tools can only read them. A limit over a period reserves its amount before approving and releases it when the approval goes unused. The page's frames are decoded again on the agent, and an instruction that can't work as written (no conditions, a limit over a period in another currency or without one amount condition) is refused on a card.
- **AG2. Agent approvals** (Operations 5, 6, 7), 0.4 only. When an operation arrives, a deterministic check compares the revision's `terms` with the User's instructions. Only a full match on the instruction's own keys approves, with `approver="agent"` and no `input_type`. A missing key, an unknown currency, a value it can't compare, or an irreversible scope hint (4.7) sends the operation to the User's card instead. A withdrawn instruction stops approvals not yet sent. **Done**: amounts compare exactly, as millionths, in the instruction's currency, and the Session must hold no scope its Company marks irreversible or leaves unhinted. The approval is sent by a job after the request that returned the operation, never inside it, and the job checks again that the card is still waiting and the instruction still stands. Following the 11 November text, which replaced "checked again", a revision answering an agent approval, and any approval after a decline, goes to the User's card. Activity names the instruction an approval rested on; the Companies page lists what each instruction approved and what it counts against its limit. Tests in [poppy-0.4.test.ts](../test/poppy-0.4.test.ts) cover APIs and MCP, each way the check refuses, the limit, withdrawal, the User deciding first, a new revision and a decline.
- **A1. Approvals across Sessions** (Operations 3; decision 43). Replace `sameAuthority`'s `sessionId` comparison with the agent, User ID and account; signed-out stays separate. **Done** for Operations 3 approvals; the withdrawal generation still has to match, so a sign-out voids them.
- **C1. Conversation state** (8.7). Done: a 0.4 conversation stores `working`, `handoff` and `responder` from reads, POST replies, `state` events and a stream's `working` events, and derives `status`, the local marker both versions share: `closed`, `queued` while a handoff is pending, `working`, or `idle` (`nextState` in [conversations.ts](../src/poppy/conversations.ts)). A read must carry all four fields. An unknown `handoff` counts as `pending` and an unknown `responder` as `human`. The mock reports 0.4's fields, adds `state` events only when `handoff`, `responder` or `closed` change, answers a POST with `conversation_id` alone, and streams `working`. Kit: `conversations.events-schema`, `conversations.closed-not-working` and `conversations.working-settles` pass.
- **T1. `tasks.endpoint`** (9), read per Session with the Session header and no token; `feedback.endpoint` comes from its response. Kit: `tasks.response`, `tasks.alternative-references`. **Done.** The response is kept per Session as its caching headers allow, never `no-store`, and a feedback endpoint it names on another host gets the Session header but no token ([reading](readings.md#v04-tasks)).
- **W1. `poppy:browser-sign-in`** (6). **Done** ([reading](readings.md#v04-browser-sign-in)): requested only from a Company with a browser-session endpoint, when the model asks for it; `web.unscoped` is shown first. The join sends a token only with the scope, and after `insufficient_scope` authorizes the same code again without one, so the browser is signed out on the website and the model is told how to change that. Mock: `webUnscoped`; TAMPERS row `browser-sign-in.no-endpoint`.

**Layer 6.**
- **R1. Retry after `version_unsupported`** (3.4): fetch `poppy.json` uncached, choose again, and send once in a new Session only if the choice changed. **Done** for API calls without an approval; a conversation request or an approved request isn't sent again under another version ([reading](readings.md#v04-version-unsupported)).
- **C2. Request IDs** (8.2, 8.3). Done: under 0.4 every conversation POST carries an `id`, stored before sending and reused on retry ([conversations.ts](../src/poppy/conversations.ts) `sendMessage`, `requestBody`). A message takes its request's ID and carries none of its own; handoff and close store theirs too. A conversation's requests use the version it started in. The mock requires the ID (`request.id`), replays a retry with the same ID, path and body, and answers `request_id_conflict` otherwise (`request.id-reused`). Kit: `conversations.missing-request-id`, `conversations.invalid-request-id`, `conversations.request-id-boundaries`, `conversations.request-id-conflict` and `conversations.request-id-other-conversation` pass; `conversations.request-id-other-url` waits for the cancel endpoint (C3).
- **T2. Skills** (9.4): the tasks response's skill index. Kit: `tasks.skill-index`. **The mock half is done**: its tasks response lists one `SKILL.md` by a reference relative to `tasks.endpoint`, with its digest, and it records an artifact fetched with a token or Session header (`skills.credentials`). - **W3. Website operations** (Operations 4 to 8.2). The reference comes only from the final response's own header, never from page content, and only when `sid` names that browser's Session. The approval goes to the operations endpoint, never through the browser, and the browser repeats exactly the approved submission; a failed or re-referenced repeat is looked up (`performed`, `performing`, `approved`). The local form-consent card stays in front. A scoped website's `poppy:browser-sign-in` doesn't stop a standing instruction, since it allows nothing beyond the other scopes (0.4 6).
