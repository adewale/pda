Guides

About the guides

The specification covers only what a company and a personal agent need to work together. These guides cover the rest: recommended practices for a secure, reliable implementation, and advice for each party.

Following the guides is not required to comply with the protocol. Each item is a recommendation, in the sense of SHOULD: do it unless you have a good reason not to. Where a guide repeats something the specification requires, it says MUST and links to the section that requires it.

Start with For both parties, then read the part for your side. The examples use the same placeholder domains as the specification: example.com for the company and agent.example for the personal agent.

For both parties

Handling secrets

These are secrets:

  • Session tokens and account tokens.
  • Private keys, client assertions, session assertions, and DPoP proofs.
  • Authorization codes, PKCE code verifiers, device codes, one-time sign-in codes, browser-session codes, and credentials sent in mediated sign-in.

To handle them:

  • Keep them out of logs, telemetry, error reports, model context, conversation messages, and URLs. Tokens MUST NOT be sent in a URL (4.3), account tokens MUST NOT go in model context, messages, logs, or URLs (4.8), and tokens, private keys, authorization codes, PKCE code verifiers, and device codes MUST NOT go in model context (9.2).
  • Redact the Authorization, DPoP, and Cookie headers and credential fields before a request reaches a logger or tracer.
  • Send Cache-Control: no-store on every response that carries a token or code.

Signing and verifying JWTs

Assertions and DPoP proofs are JWTs. To sign and verify them consistently:

  • Personal agents: sign assertions and DPoP proofs with ES256. Every company accepts it in proofs (MUST, 3.2). Companies: accept ES256 and RS256 in assertions. Use RSA keys of at least 2048 bits.
  • Reject alg: none and symmetric algorithms such as HS256.
  • Verify assertions only with keys from the personal agent's verified jwks_uri (4.1). Ignore jku, x5u, and any key embedded in an assertion. DPoP proofs are the one exception: the public key in their jwk header is how they work (4.3).
  • Check aud, exp, and iat. A client assertion or Session assertion has the company's auth.issuer as its aud, never an endpoint URL (4.1). Allow a small clock skew, such as 30 seconds, and reject assertions that claim a long lifetime.
  • Make each jti at least 128 random bits.

Rotating keys

  • Give every key a kid.
  • Publish a new key in jwks_uri before signing with it, early enough for companies' caches to pick it up.
  • Keep an old public key published until everything signed with it has expired.
  • Companies refetch jwks_uri when they see an unknown kid. The refetch happens before any signature is checked, so anyone can trigger it by naming a real personal agent and a made-up kid. Refetch each jwks_uri at most once per interval, such as 30 seconds, and count failed fetches too. Otherwise a stream of bad assertions can flood the personal agent's server.
  • Rotating signing keys doesn't affect account tokens. They are tied to the client_id, not a key (4.8).

Fetching metadata safely

Personal agents fetch poppy.json files and API descriptions. Companies fetch client metadata documents and key sets. Each fetch goes to a URL the other party controls, so:

  • Set limits: a few redirects at most, a response size such as 100 KB, and a timeout of a few seconds.
  • Validate HTTPS certificates. Personal agents MUST follow discovery redirects only to HTTPS URLs (section 3).
  • Never send cookies, tokens, or other credentials on these fetches.
  • Reject loopback, private, and link-local addresses unless you've configured them on purpose. Check the address you actually connect to, not only the one DNS returned first.
  • Cache according to HTTP caching headers, within bounds you set, such as at least a minute and at most a day. The upper bound means a removed key stops being trusted.

Retries

  • Send an Idempotency-Key on API writes that accept one. Use a random UUID (version 4), and reuse the same key when you retry the same request.
  • Give each conversation message an id with at least 128 random bits, and reuse it when you retry the message (7.3).
  • Each retry needs a new DPoP proof, and a retried token request needs a new assertion. The company may reject a jti it has already seen.
  • Wait at least as long as Retry-After says on a 429 (MUST, 4.3) or a 503.
  • Otherwise, back off exponentially with jitter, cap the delay, and limit the number of attempts.
  • Companies keep idempotency records for a set time, such as a day, scoped to the session. They return the original response for a repeated key, and reject a repeated key with a different body.

Rate limits

Personal agents change the shape of web traffic: one user's request can turn into many automated calls, at any hour. Existing HTTP patterns handle most of this.

  • Companies: limit by client_id, by user, and by session, so one busy personal agent or user doesn't crowd out others. Count a request against a client_id only after its client assertion's signature checks pass. Otherwise anyone can name a personal agent and use up its limit, so its real users are refused. Limit unverified requests by network instead.
  • Companies: also send the RateLimit and RateLimit-Policy headers (IETF draft), so personal agents can slow down before they hit a limit.
  • Personal agents: keep track of limits for each company and share them across your tasks and users, rather than letting each task find the limit on its own.
  • Personal agents: prefer long polling or streaming over repeated short polls, and check for changes no more often than the task needs. Checking once a day for a price drop is usually enough.
  • Personal agents: run work that isn't time-sensitive, such as checking order status in the background, outside the company's busy hours, and spread it out instead of starting it all at the same moment.

Transport and JSON

  • Use TLS 1.2 or later. Prefer TLS 1.3.
  • Encode JSON as UTF-8 and reject objects with duplicate member names.
  • Write timestamps in RFC 3339 with a time zone offset, such as 2026-10-02T17:15:00-07:00.
  • Ignore fields you don't recognize, so later versions can add them.

For personal agents

Finding a company

When the company you reach is on a different domain from the one the user asked for, tell the user which company you're dealing with, its organization.name and domain, before you sign in or act for them. A well-known URL can redirect to any host's /.well-known/poppy.json (section 3). A rebrand, such as oldname.example redirecting to newname.example, then costs one line, and a domain that sends you to another company can't move the user's task there without them noticing.

User IDs

Each user needs a stable, opaque ID for each company (4.2). Two ways to make one:

  • Store a random ID for each user and company the first time they're needed. This is the simplest choice.
  • Derive one with a keyed hash, such as HMAC-SHA256 of your internal user ID and the company's auth.issuer, with a secret key. Changing the key changes every ID, so the company sees all your users as new.

The ID MUST NOT contain or be derived from personal information, such as an email address, phone number, or name (4.2). This includes hashes of it, keyed or not. If you derive the ID, start from an internal ID that is itself random.

Key user IDs by the company's full auth.issuer, including any path, not by its host. A provider can host several companies on one host, such as https://auth.platform.example/outfitters and https://auth.platform.example/books, and each is a different company with its own user IDs (3.2).

Tell your users, such as in your privacy notice, that each company recognizes them across visits through their user ID, even when they're signed out, and that signing in lets the company link those earlier visits to their account.

You MAY offer anonymous browsing, like a private browser window, with a new user ID for each anonymous browsing session (4.2). The company sees a new user each time, and nothing in the protocol links that browsing to the user's regular ID, their account, or their other anonymous sessions. Other signals, such as IP addresses, still can.

  • Create a random ID for each anonymous browsing session. Its session has its own session key, as every session does, so nothing links it to the user's other sessions.
  • Discard both when the browsing session ends. Carts and conversations from it end with it.
  • Never sign in with an anonymous ID (MUST NOT, 4.2). If the user wants to sign in, switch to their regular ID in a new session.

Keep the mapping of each user's IDs across companies confidential (MUST, 4.2). Don't publish it or share it with third parties, other than service providers that process it for you.

DPoP keys and proofs

  • Generate a new DPoP key pair, the session key, for each session, and never use it for another session (MUST, 4.3). Make it non-extractable where your platform allows, such as in a key management service or WebCrypto.
  • Keep the session key for as long as you use the session. Its thumbprint names the session at the token endpoint, so a lost key means a new session.
  • Never expose private keys to a model or to tools a model can call. Sign on the model's behalf in code it can't reach.
  • Sign proofs in an HTTP client hook that sees the final method and URL. Don't let the client follow redirects from protocol endpoints with the token or proof: you MUST NOT send either to the new URL (section 3).
  • Sign proofs with ES256, which every company accepts (3.2). Use another algorithm only if the company lists it in dpop_signing_alg_values_supported.
  • Personal agents MUST support nonces (4.3). On use_dpop_nonce, take the nonce from the DPoP-Nonce header, keep it for that server, and retry once with a new proof that includes it.
  • A session can't change its key. To use a new key, start a new session.
  • After invalid_grant on a session key, never use that key again (MUST NOT, 4.2). Start a new session with a new key. A company can forget an ended session's key and start a new session for it, so don't count on a renewed session keeping its cart or browser cookie.

Storing tokens

  • Account tokens MUST be stored as secrets (4.8). Encrypt them at rest, apart from the model and its tools. Give tools a reference to the token, not the token.
  • Keep session tokens in memory and drop them when they expire.
  • Store account tokens by the company's full auth.issuer, as for user IDs, so a token from one company hosted by a provider is never sent to another.
  • Include resource in every token request for an MCP server, and use the scheme token_type names (MUST, 4.3). For an MCP server whose protected resource metadata doesn't list dpop_signing_alg_values_supported, exchange a DPoP session token for a Bearer one with the token exchange grant. Bearer tokens can be used by anyone who copies them. Each one is limited to one MCP server by resource, and you can also narrow it with scope.
  • When the company returns a new account token, you MUST use it from then on (4.8). Replace the stored one right away.
  • After the user signs in again for more scopes, revoke the old account token (4.4).
  • On invalid_grant for an account token, delete it and continue signed out.

Choosing how to sign in

  • Before asking the user to sign in, check whether an account token you hold already covers the task (4.4).
  • Prefer direct or device sign-in to mediated sign-in (SHOULD, 4.4), and direct to device sign-in (4.6). With direct and device sign-in, the user's password stays with the company.
  • Read each scope's description, from the company's OpenAPI description or auth.scopes, to pick the ones the task needs (4.4).
  • Use auth.scope_hints to decide which scopes need the user's go-ahead before you request them (4.4). For example, request a scope whose changes is irreversible, or whose personal_data is true, only when the user agreed to that kind of access, and let the user set that preference once rather than for every sign-in. Treat a scope without hints as irreversible with personal data.
  • Hints describe a whole scope. The consequences of one action still come from the action itself, such as an MCP tool's annotations, or the HTTP method: a GET doesn't change anything.
  • Ask for the fewest scopes the task needs, not every scope the company offers. For a task that only looks things up, request a read-only session token from a broader account token (4.8).
  • The user may approve fewer scopes than you asked for. Check scope in the response before continuing. A response without scope granted every scope you asked for.

Direct and device sign-in

  • Use direct or device sign-in only when the user signs in themselves (MUST, 4.4). Never type the user's password, enter their one-time code, or click the company's approval controls for them.
  • Open the authorization URL in the user's own browser, not in a browser you automate.
  • Make state random and single-use. Record which company and session it belongs to, and exchange the code only at that company's token_endpoint. Check that the redirect's iss matches that company's auth.issuer (MUST, 4.5).
  • Use PKCE with code_challenge_method=S256 (4.5).
  • If you can't receive the redirect on the device the user is talking to you on, send the authorization URL to the user, for example to their phone, with a redirect URI you control. Fall back to device sign-in only when that isn't possible (4.6).
  • Bind the code to the session key with dpop_jkt in the authorization URL, or with a proof on a pushed authorization request (MUST, 4.5). Exchange the code, and poll for device sign-in, with proofs signed with the same session key.
  • For device sign-in (4.6), show verification_uri_complete as a link or QR code, and show user_code too so the user can confirm it matches. Keep device_code private. Show the link only if its host is the company's issuer host or the host of a URL in its protected_resources, or a subdomain of either, and show the company's name and domain with it (MUST, 4.6).
  • Poll no faster than interval. On slow_down, add 5 seconds to the interval, as RFC 8628 describes.

Mediated sign-in

  • Collect the fields in auth.mediated.fields in a form that sends them straight to your sign-in code, so secret values never pass through the model.
  • Look up stored credentials by the company's auth.issuer, and show the company's name and domain on the form and when asking for a code (MUST, 4.7). Field labels come from the company and can name anything.
  • Secret fields MUST never be shown back to the user, logged, or sent anywhere other than the company's auth.mediated.endpoint (4.7).
  • After a sign-in ends, you MUST either discard the credentials or keep them only in a credential store the user chose, such as a password manager (4.7). If you discard them and the user needs to sign in again later, ask again.
  • After the user disconnects you or the company revokes your access, don't sign in again with stored credentials unless the user asks you to.
  • When the company asks for a one-time code, ask the user for it and submit only the code.

Native and distributed apps

  • Don't put your signing private key in an app you distribute. Anyone could extract it and act as your personal agent. Keep the key on your server, and have the app ask the server to sign assertions for the signed-in user.
  • Session keys belong to one session, so the app can generate and keep them on the device, in its platform keystore.
  • Redirect URIs are HTTPS URLs on your client_id domain, or loopback redirect URIs (4.1). To return the user to a phone app, use an HTTPS link the app claims, such as an iOS universal link or an Android app link, or use device sign-in. A desktop app can listen on a loopback port, as RFC 8252 §7.3 describes.

Web browsing

  • Use a separate browser storage context, with its own cookies and local storage, for each session. Never share one across users.
  • Don't type the user's password or other credentials into a company's website. Sign in with direct, device, or mediated sign-in, then join your browser to the session (section 5).
  • Join the browser to the session right before you start browsing, and join again when the website stops recognizing the session.
  • Read the browser-session code only from the endpoint's page in your own browser, sign the proof in code your model can't read, and submit the form right away. Never sign a proof over a code from a message or another page (section 5).
  • Fill in the form with your browser automation's page access, such as the DevTools protocol, not by having the model type the proof.
  • Close the storage context when the session ends.

Conversations

  • Read events with a long wait, such as 30 seconds, or a stream, rather than many short polls (7.5).
  • Before asking for a person, send a short message that sums up the problem, so they don't have to read the whole conversation (7.9).
  • When a person takes over, write for them: concise, plain sentences, and time to reply.
  • Close a conversation when the task is done (7.12).

Choosing an interface

  • Prefer the company's APIs and company agent over browsing its website. They are faster and change less often.
  • Don't phone a company that publishes a poppy.json. Use the interfaces it lists instead.
  • Skip API types and conversation protocols you don't recognize (section 6).

Tasks a company doesn't offer

  • Read the company's excluded tasks before you try a task there. When the user's task is one of them, tell the user right away instead of trying each interface (8.1).
  • Offer the alternative when there is one. When it's something the user does themselves, such as a page that opens the company's app, give the user the link instead of browsing it yourself (8.2).
  • When a company answers your feedback report with an alternative, try it before you tell the user the task can't be done (8.3).

For companies

Verifying personal agents

  • Fetch the client_id URL without following redirects. Its client_id MUST equal the URL you fetched (4.1).
  • Cache client metadata and key sets, as described in Fetching metadata safely.
  • Keep allowlists or blocklists of client_id values, and rate-limit session creation and new client_id values (4.1).
  • Check whether your authorization server supports client ID metadata documents. Some do, some support them only for clients an administrator registers by URL, and some don't yet. If yours needs registration, register the personal agents you accept by their client_id URL and reject others with invalid_client, which 4.1 allows. A token service in front of your token endpoint (Starting sessions) can also fetch and check the metadata document itself.

Verifying DPoP

Section 4.3 lists the checks you MUST make on every proof. To make them reliably:

  • Check that typ is dpop+jwt, that alg is ES256 or one you list in dpop_signing_alg_values_supported (3.2), and that jwk holds only a public key.
  • Keep a replay cache keyed by jti, holding entries for the acceptance window. Your token endpoint MUST reject a reused jti (4.3), so share its cache across every server behind it. Your APIs and conversation endpoint can have one too, ideally shared the same way. Otherwise a proof accepted by one server can be replayed at another.
  • Behind proxies and load balancers, compare htu with the public URL the personal agent used. Build it from your configured public origin, not from the Host header your server receives.
  • Use an acceptance window of about one minute, plus a small clock skew.
  • Require nonces if you want proofs that can't be made in advance. A nonce stays valid for a while, so it doesn't stop a proof being replayed. It doesn't replace the replay cache.
  • Check whether your authorization server can issue DPoP-bound tokens. If it can't, put a gateway in front of both your token endpoint and your APIs and conversation endpoint. It checks the proof on each token request, records the key for the token it issues, and checks that key on every later request. Checking a proof's signature alone isn't enough.
  • Accept a Bearer session token only at the MCP server whose url is its resource, not at other paths on the same host (MUST, 4.3).
  • If you list an MCP server that doesn't support DPoP, support the token exchange grant (MUST, 4.3). Issue Bearer tokens to personal agents only through it, and check that the subject token is bound to the proof's key.
  • Support DPoP on a new MCP server (SHOULD, 4.3): list dpop_signing_alg_values_supported in its protected resource metadata, with ES256, and verify proofs as on your other APIs. Then issue personal agents only DPoP tokens for it. Keep accepting Bearer tokens from MCP clients that don't implement Poppy, and reject a DPoP token sent as a Bearer token.
  • Serve personal agent conversations only from your conversation endpoint (7.2). If your website chat or other channels can open the same conversations, they may not check DPoP, and anyone with a copied token could read them there.

Sessions and session keys

A session is named by the thumbprint of its session key (4.3). At the token endpoint:

  • Key your session records by the thumbprint of the key in each request's proof. A known key renews or signs in its session. A new key starts a new session.
  • Reject a key that names a session for a different client_id or user ID with invalid_grant (4.2).
  • Remember the keys of sessions you end, and reject them with invalid_grant (SHOULD, 4.2). Otherwise a renewal with an ended session's key silently starts a new session. Keep them at least as long as your longest session lifetime.
  • Support dpop_jkt (MUST, 4.3), and reject a code exchange whose proof key doesn't match the key the code is bound to.
  • Bind each device_code to the key of the first poll, and return invalid_grant to polls with any other key (4.6).
  • Don't bind account tokens to a session key. One account token starts sessions with different keys (4.8).
  • Most authorization servers can't key state by DPoP thumbprint without custom code. The same custom work that starts sessions can do it (Starting sessions).

Starting sessions

Most authorization servers accept a JWT bearer assertion only for a subject they already know, so they won't start a session for a user ID they've never seen (4.2). There are three ways to handle the grant:

  • An extension to your authorization server, such as a plugin or custom grant handler. It checks the assertion as 4.2 describes and issues the session token. This keeps everything in one server, if your server allows it.
  • A token service in front of your token endpoint. It handles the JWT bearer grant itself and passes every other request through. The session tokens it issues must be ones your APIs accept, so it signs them with your server's keys or has your server mint them.
  • A user record on first sight. The first assertion for a new user ID creates a user record, which your server then accepts as the assertion's subject.

Records on first sight are the least custom code, but they have costs:

  • Your user directory fills with one record for every signed-out user, and every anonymous browsing session brings a new user ID (4.2). Keep these records apart from customer accounts, and delete ones that go unused.
  • Hosted authorization products that bill per active user may bill you for every signed-out user.

Whichever you choose, the same records hold how a session and an account token link a user ID to an account (4.4).

Token lifetimes and sign-out

  • Session tokens should last hours, not days (4.2).
  • Check on each request whether the session is still signed in, so sign-out takes effect right away. If you can't, keep session tokens to a few minutes (4.9).
  • Don't stop accepted work because the session token that started it expired. A job can outlast the token (4.9).
  • Where work in progress can take consequential actions on the user's account, such as payments or changes that are hard to undo, tie it to the account token, so revoking access stops it right away.
  • Give account tokens a lifetime that fits the account, such as 90 days, and expire ones that go unused sooner.
  • Send refresh_token_expires_in when an account token has a lifetime (4.4). An expired token and a revoked one both get invalid_grant, and the lifetime lets the personal agent tell the user which happened.
  • Revoke a user's account tokens when they reset their password or you suspect the account is compromised.

Describing scopes

Every scope in scopes_supported needs a description, in the OAuth security scheme of an OpenAPI description you list or in auth.scopes (MUST, 4.4). Personal agents read them to choose scopes, and a language model often does the choosing:

  • Say what the scope lets the personal agent see or do, in words a user understands.
  • Be specific enough for a model to match a task to the scopes it needs. "See your orders and returns" works better than "Read access".
  • Say whether the scope only reads, and whether a write scope also allows reading.
  • Say in words which actions can't be undone and what personal data the scope shows.
  • Give each scope its hints in auth.scope_hints (4.4). Judge each scope by the most consequential operation that requires it: one operation that can't be undone makes the whole scope irreversible. When you're unsure about a scope, leave it out of auth.scope_hints rather than guess.
  • Splitting a scope can earn it a better hint. A personal agent may request orders:read freely but ask the user first before requesting a scope that can cancel orders.

Describing APIs

A language model usually reads your API descriptions and MCP tool descriptions to choose and call operations (6). Write them for that reader:

  • Say clearly what each operation does and when to use it, in terms of the user's task.
  • Keep them small. The whole description takes room in the model's context, so leave out what personal agents don't need, such as long examples or operations only your own apps call.

Consent pages

The page where the user approves access, in direct and device sign-in (4.5, 4.6):

  • Show the personal agent's name and logo, and the domain of its client_id. The personal agent chooses its own name, so the domain is what the user can trust.
  • Show the account being connected, the requested scopes in plain language, and how long access lasts. Group related scopes rather than listing their names.
  • Point out scopes that allow changes that can't be undone or that show personal data, the scopes your auth.scope_hints mark irreversible or with personal_data.
  • When the user already granted some of the scopes, show which ones are new, so the user doesn't review the whole list again. A personal agent that needs more access requests every scope it needs again (4.4).
  • Protect the page against cross-site request forgery, and against framing by other sites with Content-Security-Policy: frame-ancestors.
  • redirect_uri MUST exactly match an entry in the personal agent's redirect_uris (4.5).
  • Accept PKCE with S256 only, and reject plain.
  • Return iss in every redirect, success or error (4.5). Personal agents reject a redirect without it.
  • For extra protection, support Pushed Authorization Requests (RFC 9126).

Device sign-in

  • Follow the best practices for cross-device flows in RFC 10027 §2 (MUST, 4.6): assess the risk before offering device sign-in, and choose mitigations from its §6.1, such as short-lived single-use codes, rate limits, limited scopes, and a consent page that says which personal agent is asking and tells the user to decline a code they didn't ask for.
  • Opening the link MUST NOT approve the request by itself (4.6). The same goes for scanning the QR code. The user signs in and approves on the page.
  • Ask the user to confirm that the code on the page matches the one the personal agent shows.
  • Return slow_down to personal agents that poll faster than interval, and limit wrong user_code entries.
  • Keep expires_in short, such as 10 minutes.

Mediated sign-in

Mediated sign-in is transitional (4.7). Offer it only until you can add direct or device sign-in, and plan its removal: the protocol plans to remove it, on a date set when version 1.0 is published.

If you offer mediated sign-in, you MUST rate-limit attempts and MUST NOT return credentials in any response. Also:

  • Rate-limit by account, by client_id, and by user ID, and cap wrong one-time codes.
  • Require a one-time code when a sign-in looks unusual, including a personal agent's first mediated sign-in after the user disconnected it.
  • Return the same failed response for an unknown account and a wrong password, so responses don't reveal whether an account exists.
  • Never store raw credentials or codes, including in logs, traces, and idempotency records.
  • Tell the user, for example by email, when a personal agent signs in.

Account settings

  • In account settings, list each connected personal agent with its name, domain, scopes, and when it was last used.
  • Offer a control to disconnect each one. Disconnecting revokes its account tokens and signs out its sessions (4.9).

Browser sessions

  • Offer web.browser_session_endpoint if you want signed-in personal agents to use your website. Without it, they browse your website only as ordinary signed-out visitors (section 5), and use your APIs and conversations for anything that needs the account.
  • Don't log the endpoint's responses or request bodies. They contain browser-session codes and proofs.
  • If you make the code stateless, put a keyed hash of the code and its expiry in the step 1 cookie, and still remember used codes until they expire, so each one works once.
  • Limit the cookie to the hosts personal agents need, such as your main site, rather than your whole domain.
  • Look up the session on each request, so sign-out and scope changes take effect on the website right away.

Enforcing scopes everywhere

  • Apply the same scope rules on your website, APIs, company agent, and live agents. One shared check that every channel calls is easiest to keep consistent.
  • Have the company agent's tools check the token's scopes on every call. Don't rely on the model to decide.
  • Give live agents' tools the same checks, so a person can't make a change the token doesn't allow (7.11).
  • Check read and write scopes separately. If a write scope also allows reading, say so in its description.
  • When your website refuses an action for a missing scope, show an error that names the scopes (SHOULD, section 5).

Internal services

  • Don't forward a session token from one of your services to another.
  • Verify the token at the edge, then pass the verified client_id, user ID, account, and scopes to internal services through a gateway or service credentials.
  • Internal credentials used for a request shouldn't allow more than the session token does.

The two Outfitters storefronts share an issuer, so they are one company: a user has the same user ID, sessions, and account tokens at both. Books has its own issuer, so it's a separate company, even though it runs on the same servers.

  • Publish metadata for each issuer at its own URL, such as https://auth.platform.example/.well-known/oauth-authorization-server/outfitters (3.2). Its issuer is the full issuer, and its protected_resources lists only that company's storefronts and resources, such as https://outfitters.example.
  • Serve each storefront's poppy.json on the storefront's own domain. A document redirected to the platform's domain speaks for the platform, not the storefront (3.1).
  • Companies can share a token endpoint, servers, and signing keys. Only the issuer decides which company a token belongs to.
  • Record the issuer with every session and account token, and check it on every request. A session token or account token from Outfitters must not work at Books, even when both are served by the same code.
  • Don't use one company's records for another. A user's sessions, user IDs, and accounts at one company are unknown to every other company the platform hosts.

An issuer for personal agents

A company can offer personal agents less than its other OAuth clients get without a second issuer, in two ways:

  • Leave scopes it doesn't offer personal agents out of scopes_supported, which RFC 8414 allows (3.2).
  • Limit the scopes it grants by client, as OAuth allows (4.4).

Sign-in types are different. grant_types_supported has no such allowance, and a company whose issuer offers the authorization code or device grant to other clients offers direct or device sign-in to personal agents too (4.4). To keep one of them from personal agents, use an issuer only for personal agents, such as https://auth.example.com/agents. It can share servers, signing keys, and user accounts with the main issuer.

Choose the issuer before launch. User IDs and account tokens belong to the issuer (3.2), so changing auth.issuer later makes the company a new company to every personal agent: existing sessions and account tokens stop working, and users sign in again.

Guest access

Let a signed-out personal agent session do what a signed-out visitor can do on your website, such as search products, read store policies, or ask the company agent general questions. Limit abuse with rate limits by client_id, not by turning personal agents away.

Conversations

  • Let your company agent do everything customers can do by phone, as fully as you can, so personal agents have no reason to call.
  • Keep a conversation's events for at least 30 days, so a personal agent that reconnects rarely hits cursor_expired (7.5).
  • On a stream with nothing to send, send an SSE comment every 15 to 30 seconds, so proxies don't close it (7.6).
  • When a session signs out, answer a signed-out token on its conversations that used the account with insufficient_scope, including reads of their events, so their account details can't be read signed out (4.9, 7.11). Leave them open, so the user can sign in again and continue, or close them if your policy is to clear everything at sign-out.
  • Before closing an inactive conversation, say so in a message (7.12).

Excluded tasks and feedback

  • List the tasks you've chosen not to offer to personal agents, such as ones you allow only in your app for security or regulatory reasons (8.1). Personal agents then stop looking for a way to do them, and don't send feedback about them.
  • Write each task the way a customer would ask for it, such as "Send a wire transfer".
  • Give an alternative whenever there is one. Link to the page, or the screen in your app, where the user can do the task (8.2).
  • Set caching headers on the document, and update it when you add or remove a task.
  • When a feedback report asks for a task you do offer, answer with an alternative that says how, so the personal agent can finish the task (8.3).
  • Take feedback only at feedback.endpoint (8.3). Don't offer a second feedback operation in your APIs, so personal agents don't have to choose between them.

Error messages

  • Keep error_description and other error text free of account details and other users' data.
  • Return the same error for "doesn't exist" and "belongs to someone else", as conversation_not_found does (7.13).

For the Operations extension

These apply only to companies and personal agents that support the Operations extension.

Personal agents

  • Show the user the operation's summary as the company wrote it, with the company's name and the account it applies to. Point out any cost, date, or condition, and whether the action can be undone. Don't replace the summary with your own paraphrase.
  • When a new revision arrives, show the user what changed before asking them to approve it again.
  • Store each standing permission with the company, account, kind of action, limits such as a maximum amount or number of uses, and expiry. Check every limit against the revision's terms before confirming with standing_permission. If a term you need to check is missing from terms, ask the user instead.
  • For a permission with a limited number of uses, reserve a use before you confirm, so two tasks running at once can't both use the last one. Release the reservation if the company rejects the confirmation.
  • After a confirm times out, read the operation or confirm again with the same revision. Wait for Retry-After between reads.

Companies

  • When you call another system to perform the action, such as a payment processor or a warehouse, derive its idempotency key from the operation ID. A retry then can't perform the action twice downstream either.
  • If a downstream call times out, ask that system whether the action happened, using your business reference, before trying again. Keep the operation in_progress until you know.
  • To spot the same action coming up in another channel, look for an open operation in the same session or account with the same terms before proposing a new one.
  • Keep final operations readable for as long as the user can see the related order or booking on your website, or at least 30 days.
  • Write the summary so it stands alone: what will happen, to what, and any cost, date, or condition. Personal agents show it to users as is.
